# hz11f の実データで見つかった問題の改修（2026-10-22 b）

hz11f（pursuit-r1 = E1R、direct-r1 = D0、各 5 課題）は両条件とも 10/10 正答で終わった。台帳を読み直すと、正答の陰で次の問題が起きていた。数値は `hz_author_private/hz11/evidence_hz11f.ts` の出力による。

## §1 範囲の拡大（scope_growth）と保護的な巻き戻し

問題: `scope_growth` が 4 回発火し、うち 2 回は本物の進捗を巻き戻した。

- legacy-billing の判断 #4: 仮説 H2 は「anniversary.py と credits.py と pricing/ の 4 ファイルを直す」一つの直しだった。試行 #6（write anniversary）、#7（write credits）、#8（run で 4 ファイルを書き換え）が、それぞれ「まだ変えていなかったファイル」を足したので 3 回続けて数え、発火した。保護的な巻き戻しは `scope_growth` を損傷とみなしていたので、6 ファイルの直しが消えた。
- sales-pipeline の判断 #7: `bash build.sh` の出力 `build/sales.db` と `out/report.txt` が課題のファイルとして数えられた。巻き戻しの一覧は約 50 件（大半が scratch）で、それが 3 回の要求に繰り返し載った。

原因: 「範囲」を「変えたファイルの集合」としていた。複数ファイルにまたがる一つの直しも、コマンドの生成物も、範囲の拡大に見える。巻き戻しの判定が、この兆候だけで作業を消していた。

改修:

1. 仮説は `targets`（変えるつもりのファイルかディレクトリ、最大 30、既定 `[]`）を宣言できる。台帳は migration `pursuit-0006-hypothesis-targets` の `pursuit_hypothesis.targets_json`。仮説の要求は、作業領域を変える道具があるときだけ書き方を示す。宣言は以後の要求に「変える対象（宣言）」として載る。
2. 範囲は「宣言した targets」と「その仮説ですでに課題のファイルを変えたディレクトリ」。宣言がなければ、最初に変えた試行のディレクトリが範囲になる（拡大とは数えない）。試行が範囲の外のファイルを初めて変えたときだけ「拡大した」と数え、それが `scopeGrowth` 回続いたら兆候が出る。読むだけの試行は数えず、拡大しなかった変更の試行で連続は切れる。同じディレクトリでいくつのファイルを直しても拡大ではない。
3. 生成物は課題のファイルではない。生成物とは、追求の最初の仮説の checkpoint に無く、かつ作業領域を変える道具の `path` 入力として一度も名指しされていないファイル（コマンドが作ったもの）。ホストは `WorkspaceChanges.filesCreated` で checkpoint に無かったファイルを示す。示さないホストでは生成物の判定をしない（従来どおり）。試行の特徴量に `generated` として残す。scratch のパスは生成物にも数えない（別に扱う）。
4. 保護的な巻き戻し（`policy.restore = "protective"`）は、損傷の証拠（`protected_touch`、`goal_drift`、実行前の判定者の警告）があるときだけ戻す。`scope_growth` や `revisits` だけでは戻さない。
5. 巻き戻しは scratch のディレクトリを戻さない。`WorkspacePort.restore(checkpoint, { dirs })` は、その名前の段を含むパスを今の状態のまま残す。判断の basis は `reverted`（戻した課題のファイルだけ）、`revertedGenerated`（戻した生成物の件数）、`keptScratch`（残した scratch の件数）。
6. 巻き戻しの知らせは短くする。課題のファイルは 20 件まで名指しし、残りは「ほか N 件」。生成物と scratch は件数だけを書く。

再現テスト: `test/scenario/scope-restore.test.ts`（両事例を台帳の試行列で再現し、発火しない・戻さないことを確かめる）、`src/domains/rules/test/rules.test.ts`（台帳の filesTouched による規則単体の再現）、`eval/tools/test/workspace.test.ts`。

## §2 記録した知見の見え方

問題: 125 の要求が、知見が記録されているのに「（まだありません…）」と書いていた。

原因: `findings: "verified"` では未確認の知見を表示しない設計で、生成器が記録する知見はすべて未確認だった（照合で昇格するのは受入条件の検査からの知見だけで、作業課題では起きない）。表示しない理由も件数も書かず、「まだありません」とだけ書いていた。

改修: verified で未確認の知見を表示しないときは「照合済みの知見はまだありません」とし、記録した未確認の知見の件数と番号（最後の 10 件）を書く。本文は表示しないが番号での引用はできる。`findings: "all"` では、方針・仮説・提案・見直しの 4 つの要求すべてが未確認の知見を「未確認」と付けて表示する。評価の hz11g は `all` で走らせる。

テスト: `test/scenario/held-findings.test.ts`。

## §3 成り立った仮説を行き止まりと記録しない

問題: sales-pipeline の F17・F20 は、仮説が成り立って次の小問題へ進んだのに「仮説「…」は進まなかった」と記録された。

原因: 一段上へ戻るたびに、理由を問わず行き止まりを記録していた。

改修: 生成器自身が一段上へ戻り、兆候が出ておらず、その仮説の最後に実行した試行が成功で、予測した状態と一致し、機械判定できる `refutedIf` が成り立たなかったときは、仮説は成り立ったとみなし行き止まりを記録しない。それ以外（兆候による強制、反証の成立、判定できない反証、予測外の状態）は従来どおり記録する。

## §4 切り詰めの印

問題: 古い印「この一覧での表示はここまで。実物は省略されていない」が 93 回出ていた。観測以外の表示（入力・予測・知見の文など）の切り詰め `clip` が出していた。観測は v1.7 の `observationText` が切っており、最後の観測の上限 8000 字を超えた観測は hz11f で 0 件だった（実行の道具が出力を 6000 字で切るため）。

改修: `clip` の印を「表示は全 N 字のうち先頭 M 字。台帳には全文がある」にした。D0 の `eval/direct.ts` も同じ。
