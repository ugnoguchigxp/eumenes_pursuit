# Fixes after hz11h (2026-10-22, d)

hz11h: pursuit 4/5, direct 3/5. These are the follow-ups. Each section names the root cause and
the change. §1–§2 are about task design and checks, §3 about the harness.

## 3. Harness

### 3.1 refutedIf judged on the full observation

Root cause: the env `run` tool clips stdout/stderr to 6000 characters (head + tail) before it
returns. The engine stored only the clipped output, and `refutationHeld` searched that. In
hz11h-pursuit-r1 billing #3, `not_contains:"=== kumobill/pricing/engine.py"` was labelled
「反証の条件に当たった」 because the file header sat in the 4112 clipped characters, although the
command printed it.

Change: `ToolOutcome.unclipped` (optional) carries the full text of whatever the host clipped.
The engine stores it on the observation (`Observation.unclipped`); it is never shown. A
`contains` / `not_contains` needle is searched in the output and in `unclipped`. When an
observation has `unclipped`, the label says so: 「表示は一部省略だが、判定は省略部分を含む全文で行った」.
This tells the reader that a verdict may rest on text they were not shown, so they do not
misread it. Without the note, a clipped display could make a correct 「当たらなかった」 look
wrong.

### 3.2 Dead ends and F numbers

Root cause: host-recorded dead ends take the next F number. A generator that expected its next
finding to be F(n) found F(n) taken by a dead end it never sees in the findings list. Dead ends
are shown in their own section.

Change: the proposal request states 「次に記録される知見の番号は F<n> から」, and that host dead
ends share the series. The dead-end header says the same. Separate D numbers were rejected: the
ledger, the rejection notes and existing citation checks all use one series. A second series
would make 「F3」 and 「D3」 both valid, and reading old ledgers would become ambiguous.

### 3.3 F references inside new finding statements

Root cause: the citation existence check covered message / uses / refute / assessment / acceptance
checks, but not the text of a new finding.

Change: a warning, not a rejection. A statement that cites an F number that is neither in the
ledger nor taken by the same batch is recorded with
「［注: F9 は記録の時点で台帳にない番号］」 appended. Why not reject: findings are recorded before
the move checks, and the rejection notice already tells the generator that a rejected proposal's
findings stay in the ledger (fixes c §5). Rejecting the move would not remove the dangling
reference, and it would throw away a valid move over a citation in a side note. The mark stays
with the statement, so every later reader sees it.

### 3.4 Verdict labels: refutation first

Root cause: `verdictText` checked the status mismatch before refutedIf. For example, an attempt
with expectedStatus error, an observed ok, and refutedIf `status:error` (not met) read
「予測と違う（状態が予測と違う）」. That contradicts the refutation-first labelling.

Change: a machine-checkable refutedIf decides the label, and the status is said alongside it:
- 「反証の条件に当たらなかった（状態は予測の error ではなく ok）」
- 「反証の条件に当たった（…）」

Only without a checkable refutedIf does the label read
「予測と違う（状態は予測の ok ではなく error）」. The engine's held-hypothesis rule is unchanged: it
still requires the status to match.

### 3.5 Review tally

Change: the reviewed hypothesis reads
「この振り返りの対象（実行した試行 N 回: 反証の条件に当たらなかった a・当たった b[・予測と違う c]・未判定 d）」.
It uses the same verdicts as each attempt line, and an interrupted attempt counts as 未判定.

### 3.6 Give-up notice (eval)

`endNoticeText` takes the ending as well. After a give_up it says
「終わり方: 断念（give_up）。理由: …」, and after a host stop (claim limit, step limit, consultations)
it says 「終わり方: ホストが打ち切った。理由: …」. Both D0 (the last transcript entry) and E* (the last
decision) report it.

### 3.7 awk and sqlite3 (eval): documented

Root cause: the sandbox binds /usr read-only but not /etc/alternatives. Debian's /usr/bin/awk is
a symlink through it, so the link dangles; sqlite3 is not installed at all. In hz11h, one D0
messy-ledger run lost a step to 「awk: command not found」, and one pursuit attempt did too.

Change: the run tool description says 「awk と sqlite3 コマンドは無い（集計や SQLite の読み出しは
python3 で）」 and that python3 includes the sqlite3 module. I documented the gap instead of
binding /etc/alternatives: the environment stays the one every earlier run had, so the change
alters only what responders read, and a test pins both the absence and the wording.

### 3.8 show.sh status line (author tool)

`make_run_dirs_i.py`: when NOTICE blocks were printed and no request follows, the last line still
begins with 「no request yet」 / 「runner exited」 and says 「(上に NOTICE N 件。要求ではない)」. The
last line alone tells a reader what the call returned; old prefixes still match.

## 1. hz11-sales-pipeline: branch order wording (task design defect)

docs/report.md said 「支店名（branches.json のキー）の順に」. The hidden check (and the visible
truth) order branches by name (`ORDER BY branch`, as the shipped stage4 already did). The text can
also be read as "in the order the keys appear in branches.json" (tokyo, osaka, sapporo, honolulu).

In hz11h, 3 of the last 4 responders read it the second way and changed a correct ORDER BY into
key order. Replaying hz11h-pursuit-r1's own fix scripts (#6, #7, #10) on the initial tree scores
0/5 on the host-side hidden check. With only the two ORDER BY clauses restored, the same tree
scores 5/5 and matches the visible truth. So both failed claims came from the order alone:
every other fix it made was right.

This is ambiguous and is a defect in the task. The new wording is
「支店名（branches.json のキーの文字列）の昇順（文字コード順。branches.json に書かれた並び順ではない）」,
and the TOP lines read 「MONTHLY と同じ支店の順」, with ties broken by 「カテゴリ名の昇順〔文字コード順〕」.
This states the spec without pointing at any seeded bug, since the shipped code already sorts
this way. The hidden check is unchanged. The private record is `pipeline/CHANGES.md`, which also
moves the private-data version.

## 2. hz11-black-box (D0 in hz11h): an honest miss

The device's `a` cycles the multiplier 1→2→3→4→1. The D0 responder's predict.py lets it grow
without bound. Over 3000 random inputs, all 28 disagreements contain four or more `a`; no other
rule is wrong, and the ee/e corner is right. The responder itself named 「a を多数重ねたときの
倍率の上限の有無」 as an unprobed case. It spent its 12 probes without testing that case, then gave
up after one failed claim. The check is fine and nothing changes.
