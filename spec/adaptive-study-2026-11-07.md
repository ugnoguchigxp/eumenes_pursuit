# 適応的な追求と継続実行の小規模検証

## 目的と範囲

ユーザーの指摘3〜5に対応する。方式の選択はLLM、費用・期限・状態・検証契約の強制はコードが担当する。既存のengine、SQLite台帳、deferred tool、AcceptancePort、ホストの会計を再利用する。既存の未コミット変更は保持する。新規依存、既存課題の期待値緩和、モデル名・問題文による専用分岐、コミット・公開は含めない。

ユーザーの追加指定により、人間査読を必要とする証明問題を使わない。唯一の正解・最適解を要求しない調査課題を2題に固定する。解釈・提案の意味的正しさは自動保証と呼ばず、実験の実施、観測の出典、報告の数値・状態を機械で照合する。未解決という結論も許す。課題を追加して成績を選別しない。

## 実装順と依存関係

1. AUTO条件でLLMがD0/E1Rを選ぶ。目標、使える道具、モデル、予算を渡し、選択理由と計測を保存する。選択の費用・時間・要求数も予算に含める。
2. 上位レビューを既存の保留道具として接続する。予約をengineと同一transactionで保存し、送出済み不明の自動再送を禁止し、結果を保存してから既存completeToolで採用する。
3. 評価jobを同一追求・同一作業領域・同一会計scopeで再開する。設定不一致や未対応課題の復帰は拒否する。
4. 全試行の費用・時間、正しい結末あたりの総費用・総時間、照合の確かさを併記する。ホスト照合と独立した真偽の証拠を区別する。
5. 2題だけでD0/E1R/AUTOと教訓の有無を小規模比較する。上位レビューを含む追求で計画的なプロセス再起動を試す。

## 検証と完了条件

- 変更前: 指標・直接解法・プロセス復旧・保留の既存試験は成功。今回の変更前からの差分を保持する。
- 部分: 選択判断の入力境界、予算、未知費用、検証根拠、checkpointの契約を確認。
- 結合: 永続SQLiteを再openし、保留中の上位レビュー、採用済みの結果、作用重複防止を確認。
- 通し: `bun run verify`、`bun run build`。その後ソースを固定し、2題の実API検証。実行中はソースを編集しない。
- 30分または50道具呼出は持続実行の観測条件。待ち時間の水増しや無用な呼出で満たさない。自然に早く完了した場合、持続時間の実証は未達と記録する。
- 検証器は既知の正例・不正な観測参照・改変された数値・未提出などの負例で点検する。自動照合を数学的健全性や自由記述の品質の保証と呼ばない。
- 2題・各条件1回は動作確認であり、一般的優位性や教訓の因果効果を主張しない。
- 有料検証には既存会計の独立campaign上限を設け、従来の総額上限を維持する。上限の引上げや不明費用の削除は行わない。
