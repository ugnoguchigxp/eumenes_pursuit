# ablation-1: 追求の構造は直接解法より役に立つか

作成日: 2026-10-22
状態: 実装済み（ブランチ ablation-1）。実行はまだ。

## 問い

同じ課題・同じ道具・同じホスト側の照合（厳密な照合、隠された環境の検査、カナリアの検出、同じ採点基準での採点）のもとで、追求の構造（方針・仮説・反証できる予測・知見の台帳・自己評価・完了の判断・一段上へ・振り返り）が、直接解かせる場合より結果をよくするか。

## 条件

| 条件 | 中身 |
| --- | --- |
| 追求（E1R） | 今までの E1R（`--findings verified --self-check parts --verify-on claim --prediction falsifiable --completion-check acceptance`）に、下の二つの修正（`--claim-feedback verdict --attempt-count mutating`）を足したもの |
| 直接（D0） | 追求の機関を使わない（`eval/direct.ts`）。毎回、目標・受入条件・道具・これまでの行動を見せ、行動を一つ選ばせる（道具を 1 回使う／完了を申告する／断念する） |

D0 で同じにしているもの:

- 課題・道具（同じ `TaskInstance` の `tools`。秘密の値を伏せる処理も同じ）。
- 完了の申告の照合（同じ `acceptance.verify`）と、終わるときの最終の照合（追求の `finish()` と同じ）。
- 申告の結果の返し方（`claimVerdictText`。追求の `--claim-feedback verdict` と同じ文面）。不合格でも終わらず、続けられる。
- 予算（追求全体の予算に合わせる）: 道具の呼び出し = `budget.attempts`、壁時計 = `budget.wallMs`、応答の要求 = `min(budget.transitions, --max-steps)`。止まったときの理由の文面も追求と同じ（`isForcedStop` で強制停止として数える）。
- 履歴の見せ方: 1 件ごとの切り詰めは、追求の「この仮説での試行」と同じ（入力 600 字、観測 1800 字）。直近 40 件（`--direct-full-entries`）は全文、それより古いものは一行の要約。
- system の文面: 追求の executor の規則から構造に関わるもの（方針・仮説・予測）だけを除いたもの（受入条件を変えない、示せない完了を申告しない、許されない道具を使わない）。

D0 にないもの: 計画、仮説、予測（反証の条件を含む）、知見、方針の部品と自己評価、完了の判断（受入条件ごとの判断）、一段上へ、振り返り（reviewer）、相談、規則層の拒否（同じ失敗の繰り返し、予測なしなど）、作業領域の巻き戻し。無効な応答（形式違い・存在しない道具・許されない道具・JSON でない入力）は道具の呼び出しに数えず、履歴に残す。形式違いが 3 回続いたら止める。

## 記録

`runs.jsonl` の記録は両方の条件で同じ形にする。

- `mode`（pursuit / direct）、`toolCalls`、`responderRequests`（生成と振り返りの要求。採点は数えない）、`claims`、`failedClaims`、`durationMs`。
- 正しさ・偽の完了・止めすぎ（`withOutcomeFacts`。hz10u はホストの事実で数える）。
- 最後の照合の診断（`TaskInstance.diagnostics()`、ホストだけが見る）: `canaryHits` と `canaryKinds`（phrase / file / collect の種類だけ。カナリアの文面は残さない）、`graderVerdict`、`answerCorrect`、`hiddenPassed` / `hiddenTotal`。
- `budgetTag`（policy ファイル名。`v5` / `v5-tight`）、`corpus`（その実行の資料サーバの URL と要求ログ）。
- D0 の経緯は `eval/results/<run>/direct/<task>-r<k>-<id>.jsonl`（台帳の代わり）。

比べ方: `bun eval/analyze.ts --compare <run> …`。群（hz10u / hz10e / hz10a）× 方式 × 予算ごとの行と、課題ごとの行（繰り返しごとの ○× と道具の呼び出しの平均）を出す。

## 追求側の二つの修正（既定は off。以前の実行はそのまま再現できる）

1. `--claim-feedback verdict`（`conditions.claimFeedback`）: 完了の申告の結果（合格/不合格と、課題が返す照合の要約）を、そのあとの計画・仮説・提案・振り返りのすべての要求に書く。直近の申告が不合格なら、そのことをはっきり書く。合格した申告は課題を終わらせるので、そのままでは生成層に届かない。`--llm file` では、課題が終わるたびに `<llm-dir>/notices/<pid>-<n>.txt` に「前の課題は終わった・最後の申告の照合」を書き、run ディレクトリの show.sh が次の要求の前に一度だけ表示する（断念や予算切れのあとの最終の照合の結果は知らせない）。D0 も同じ旗で同じ知らせを出す。off のときは、今までどおり、今の仮説の試行と提案の要求の中にだけ出る（一段上へ戻ると、計画と仮説の要求からは見えなくなり、合格は届かない）。
2. `--attempt-count mutating`（`conditions.attemptCount`）: 仮説ごとの試行予算（policy の `attemptsPerHypothesis`）に数えるのを、作業領域を変える道具（`sideEffect: "workspace"`。書き込み・実行・提出）だけにする。資料を読む・取得するだけでは予算が尽きず、一段上へ戻らない。追求全体の試行予算（`budget.attempts`）は、今までどおりすべての試行を数える。hz10a の solo の実行では、4 課題とも資料の取得だけで仮説の予算（6）を使い切って一段上へ戻っていた。

## 天井への備え

強い応答者は以前 14/14 を通した。正しさで差が出ないときのために:

- 効率（道具の呼び出し、応答の要求、時間）を両方の条件で記録する。
- 予算を半分にした `config/policy.v5-tight.json`（道具の呼び出し 60、壁時計 45 分、手順 450。他は v5 と同じ）を、両方の条件で選んで回せるようにする。

## 公平さについて分かっている危うさ

- 同じ応答者が複数の実行に出ると、課題（答え・カナリアの位置）を覚える。実行ごとに新しい応答者を使い、順番を入れ替える（r1 は追求→直接、r2 は直接→追求、r3 は追求→直接）。horizon-10 の solo の実行に出た応答者は使わない。
- 道具の説明と選択肢の説明は、どちらの条件でも各課題の最初の要求でだけ全文を見せる（run ディレクトリの show.sh）。追求では要求の数が多いので、同じ説明を読む回数が違う。見せる量は揃えたが、読み直せる回数は揃っていない。
- 追求は 1 回の道具の呼び出しに 1 回以上の要求（計画・仮説・提案・振り返り）を使う。予算は道具の呼び出しと壁時計で揃え、要求の数は効率の指標として比べる。壁時計には応答者の速さが入る。
- D0 にない「規則層の拒否」と「作業領域の巻き戻し」は構造の一部として扱う（D0 では保護されたパスへの接触を記録するだけ）。
- 申告の結果が 合格/不合格 で返るので、どちらの条件でも申告を繰り返して当てにいける（hz10u では解けるかどうかの手がかりになる）。申告の回数（`claims`）を記録して比べる。
- hz10a のカナリアは固定で、資料も全実行で同じ（実行ごとに別のポート・別の要求ログ。資料のダイジェストは run ディレクトリの READY に書く）。ポートの番号は `{{BASE}}` として本文に入るので、実行ごとに URL の数字だけが違う。
