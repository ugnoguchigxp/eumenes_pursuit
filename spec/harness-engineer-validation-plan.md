# Harness Engineerの着手判断計画

2026-11-12 · 最初の作業はM0の対象選定。 [長期開発計画](long-term-pursuit-plan.md)

## 目的と進め方

Pursuitの実行上の問題を診断し、変更を一つ提案し、現行との比較結果を返す仕事に、専用エージェントを作る価値があるかを判断する。現在、着手条件を満たす問題は特定できていない。最初はM0だけを実施し、結果を報告する。M1以降は、直前の段階の進行条件を満たした案件に適用する。

- 実行対象のPursuitでは、現行のモデルと推論設定を固定する。比較作業の担当をGrokにする場合、通常依頼と手順付き依頼の両方で、同じGrokのモデル・推論設定・接続を使う。
- Steerの再測定、50区画の再実行、初回報告の書式エラー、修正済みの二重作成は対象外とする。Solver、Optimizer、Evaluator、SkillSmithの改善全般はこの計画に含めない。
- `eval/trace.ts`、既存の比較実行器、固定応答、ホストの受入検証を利用する。M4の条件が揃うまでは、通常の依頼と再利用できる手順で比較する。
- 初回1件、未使用2件は着手判断のための暫定件数とする。各比較の時間、モデル呼出数、費用の上限は対象を選んだ後、実行前に両方式共通で記録する。

## M0 現行版の未解決問題を1件選ぶ

### 読むものと操作

1. リポジトリ直下で `git status --short` と `git rev-parse HEAD` を実行する。現行コミットと対象機能に関係する作業中の変更を記録する。既存の変更と実行記録は編集しない。
2. `artifacts/` と `eval/results/` から、未完了・誤判定・手動復旧を含む実行を探す。まず実行日時が新しい3グループを確認する。グループは同じ比較計画または同じ実行名のまとまりとし、`manifest.json`、`summary.json`、`comparison-audit.json`、`runs.jsonl` のうち存在する集計を読む。集計が関連する別の実行を指していれば、その記録も確認する。結果がなければ確認範囲を記録する。
3. 候補の実行ごとに、`result.json`、イベント、台帳、提出物のうち必要な記録を開く。台帳がある場合は下の読取り専用コマンドを使う。実行時の設定と対象箇所を現行版と照合し、修正済みの事象を候補から外す。
4. 同じ失敗が別の実行でも起きたことを、操作・判断・受入条件のどれが一致したかで確認する。原因が未確定なら仮説として書く。影響は、正しい成果の未提出、誤った完了、必要になった手動復旧など、原記録で確認できるものを挙げる。
5. 成果への影響と人手で行った復旧や確認の内容が分かる候補を1件選ぶ。対象の失敗を検出し、正常例を通す判定方法を一つ特定する。既存の受入検証、または台帳やイベントの記録を使って機械的に判定できる条件を書く。判定に足りない情報があれば、その情報を記録する。

```sh
git status --short
git rev-parse HEAD
rg --files --no-ignore artifacts eval/results -g 'manifest.json' -g 'summary.json' -g 'comparison-audit.json' -g 'runs.jsonl' -g '!**/worktree/**' -g '!**/node_modules/**'
bun eval/trace.ts --ledger '<既存SQLiteのパス>' '<追求IDまたは課題名>'
```

### 成果物と判定

`artifacts/harness-engineer/<実行名>/m0.md` に、次の項目を保存する。対象を選べなかった場合も同じ形式で記録する。

| 項目 | 記入する内容 |
| --- | --- |
| 判定 | `進行`、`見送り`、`判定保留` のいずれかと理由1文 |
| 現行版と確認範囲 | コミット、関係する未コミット差分の有無、確認した実行名 |
| 事象 | 期待する動作、実際の動作、成果への影響 |
| 2件の根拠 | 各実行の設定と対象版、追求ID、試行番号またはイベント行、ファイルパス |
| 人が行った作業 | 調査、再提出、手動復旧など確認できた作業。所要時間が不明なら `未計測` |
| 合否判定 | 使う検査またはログと、正常・失敗それぞれの期待結果 |
| 残作業 | M1で再現する状態、または判定に不足する記録 |

- **進行**。現行版に当てはまる別々の実行2件、実害、人が行った対応、機械的に照合できる合否条件が揃った。
- **見送り**。確認した範囲に条件を満たす問題がない。調査範囲と除外理由を残してM0を終える。
- **判定保留**。候補はあるが、実行版、原記録、検査のいずれかが不足している。必要な記録を一つずつ示してM0を終える。

M0は保存済み記録の確認で完了する。モデル比較、製品コードの変更、新規テストの実装は後続段階で扱う。

## M1 変更1箇所の効果を測る

**入力**はM0で選んだ1件、原記録、既存の受入検証。まず、既存の指示、判断入力、ツール説明、比較実行器を読み、観測された事象と原因仮説を1文ずつ書く。

1. 実行前に `manifest.json` へ、元のコミットと入力、変更対象のファイルと箇所、検査、モデル設定、権限、予算、予定試行を記録する。測る失敗と期待結果を一つずつ指定する。
2. 対照は現行版とする。候補は指示、ツール説明、判断に渡す証拠のうち1箇所を変更する。既存の仕組みを利用し、課題や観測済み発話に専用の分岐を加えない。採点器、期待値、権限、採用判定は固定する。
3. **部分検証**で元の失敗例と正常例にM0の判定方法を適用し、期待どおり不合格・合格になることを確かめる。次に**結合検証**で固定応答を使い、同じ状態で比較を開始し、モデルに渡す内容の差分が意図した1箇所だけであることを確かめる。
4. モデルの判断を測る場合は、固定応答が通った後に既存の実行器で短い対比較を行う。実行と採点のコマンドは対象決定後に `manifest.json` に記録する。既存の入口で同じ状態を作れない場合は、足りない機能と最小の接続方法を特定し、対象の範囲で対応する。実行できなかった比較は判定保留とする。
5. `results.jsonl` に全予定試行の実行結果、採点、使用量、根拠ファイルを記録し、`m1.md` に差分と判定を残す。採用候補の差分に対し、必要な通し検証を実施する。省いた検証は、理由と未確認の挙動を記録する。

比較条件と再開経路に関係する変更では、以下の既存試験を対象にする。製品コードを変更した候補を採用判断へ進める場合は、対象環境で `bun run verify` を実行する。Optimizerの隔離実行と計測は既存のLinux手順を使う。 [比較条件の検査](../eval/experiment.ts) · [Optimizerの実行手順](../examples/optimizer/README.md)

```sh
bun test ./eval/test/experiment.test.ts
bun test ./eval/test/runner-contract.test.ts ./test/scenario/process-recovery.test.ts
bun run verify
```

**進行条件**は、対照で狙った失敗が観測され、候補で減り、成果の受入と終了判断に悪化がないこと。対照で失敗が出なければ判定保留とする。候補が同等か悪化なら、その変更の検証を終える。

## M2 通常の依頼と手順付き依頼を同じ条件で比較する

**入力**はM0の問題と、M1で固定した開始状態・検査・実行条件。M1の診断結果、変更案、比較結果は両方の担当から伏せ、採点時に参照する。両方式は同じ元の版、ログ、受入条件、ツール、時間・費用上限を使い、別セッションと別作業領域から開始する。

### 依頼文

**両方式の共通文**

> 渡したPursuitの実行記録から、記載された失敗を調べてください。原因仮説を一つ示し、変更候補を一箇所に絞り、現行と候補を渡した検査で比較してください。原記録の位置、差分、実行コマンド、採点結果、採用または見送りの理由を返してください。作業は指定の範囲と予算内で行ってください。

**手順付きの方式に追加する文**

> まず失敗の試行番号と、その判断前に使えた証拠を記録してください。次に、現行で同じ失敗を再現してください。再現できたら、原因仮説を一つ立て、その仮説を検証できる変更を一箇所だけ作ってください。固定応答で比較条件を照合し、既存の採点で現行と候補を実行してください。記録の不足、再現不能、上限到達時は、確認できた事実と続行に必要な情報を返してください。

### 計測と判定

- 人が操作した区間ごとに、方式、開始・終了、作業の種類、理由を `human-work.jsonl` に記録する。方式固有の資料準備、補足説明、再実行指示、採点結果の確認、差分の手直しを含める。人の作業時間は区間の長さの合計とする。共通準備は両方式に同じ扱いで記録し、処理の待ち時間は実行時間として扱う。
- M1と同じ受入条件で両方式の成果を照合する。未完了、タイムアウト、APIエラーは予定試行に残す。人の時間が記録できなければ、人手削減の判定は保留とする。
- `m2.md` に方式ごとの採点、人の作業分数・介入回数、モデル呼出数、費用、差分と原記録への参照を残す。

**進行条件**は、手順付きの方式がM1と同じ基準で改善に到達し、通常依頼より人の作業時間が減ること。同等か悪化なら、この用途での手順の導入を見送る。

## M3 未使用の2件で再現する

1. M0からM2までの再現や調整に使っていない同種の実行を2件選び、選定理由、入力、採点方法、予算、実行順を先に固定する。
2. M2の2方式を各事例で1回ずつ実行する。1件目と2件目で方式の順を入れ替える。各方式の終了まで同じ依頼文を使う。対象の失敗を検出する部分検証、通常の入口を通る結合検証、実案件に相当する通し検証の順に確認する。
3. `m3.md` に2件それぞれの採点と人の作業時間を載せ、元の試行まで辿れるようにする。新しいケースが揃わなければ判定保留とする。

**進行条件**は、2件とも手順付きの方式で対象の失敗が減り、品質が維持され、通常依頼より人の作業時間が減ること。条件を満たした段階では、手順を既存の実行環境で再利用する。

## M4 専用エージェントの着手を決める

1. M3の `human-work.jsonl` から、手順を使っても人に残った作業を確認する。比較実行の管理、中断からの再開、証拠と採点結果の結び付けなど、繰り返し発生し、既存の手順だけでは負担が残った工程を一つ選ぶ。該当工程がなければ、既存環境での手順の再利用を採用して終える。
2. 選んだ工程だけを既存の台帳、実行器、受入検証につなぐ試作にする。実装前に既存の指示、情報、道具、共通機構で扱えない条件を記録する。意味判断はLLMに委ね、コードは実行、記録、再開、権限と予算の強制を担う。
3. 部分検証で入出力と失敗時の記録を確認する。結合検証では固定応答で対象の通常経路を通し、再開を扱う場合は確定済みの操作や採点を二重に実行しないことを確認する。通し検証では同じ実案件1件をM3の手順と試作で扱う。採点・モデル・予算を揃え、対象工程にかかった人の作業時間を比較する。
4. `m4.md` に試作の差分、再利用した機構、採点、削減された作業、維持が必要な作業、採否の理由を残す。差分を見直し、個別例向けの分岐や無関係な変更を除く。

**着手条件**は、実案件で同じ品質を維持し、試作で対象工程の人手がさらに減ったこと。満たさなければ再利用手順で止める。

## 結果を引き継ぐ

各段階の報告は、判定、根拠、保存先、次の一手を含める。比較の途中で失敗した場合は、実行条件・環境・対象の失敗のどこに原因があるかを調べ、再実行するなら変わった条件を記録する。予算超過や使用量不明で比較できない場合は判定保留とし、元の試行を保持する。

Grokへの最初の依頼は次の文で始められる。

> `spec/harness-engineer-validation-plan.md` を読み、M0を実行してください。保存済み記録だけを使って対象を1件選定し、`m0.md` に根拠と判定を残してください。判定が出た時点で報告してください。
