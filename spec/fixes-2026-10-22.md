# 評価で見つかった問題の改修（2026-10-22）

対象: horizon-11 の評価（hz11u）とレビューで挙がった項目 a〜i。各項目は独立したコミットで、それぞれに試験を付ける。接続契約は v1.7（[host-contract-v1.md](host-contract-v1.md)） に追記する。

原則は [改修計画書](improvement-plan-2026-10-22.md) と同じ。意味の判断は LLM に残し、語句辞書・題材別の分岐・固定応答は足さない。規則層が見るのは構造（台帳の行・道具の副作用・パス・ID）だけである。

## a. 一段上へ戻るときの巻き戻しを黙って行わない

問題: 振り返りで仮説を捨てるとき、`policy.restore`（`always` / `protective`）の条件に当たると、作業領域を仮説の checkpoint に戻していた。そのことを生成器には伝えていなかった。生成器は、自分が書いたファイルが残っている前提で次の仮説を立てていた。

変更:

- `conditions.rollback`: `"notify" | "keep"`（既定 `"notify"`）。いつ戻すかは従来どおり `policy.restore` が決める。
  - `notify`: 戻す前に `WorkspacePort.changesSince(checkpoint).filesTouched` を取る。そのファイル一覧（ソート済み）と、その時点の試行数を判断の根拠 `basis.reverted` / `basis.attemptsAtRevert` に残す。次の試行が走るまでは、方針・仮説・提案の要求に「作業領域の巻き戻し」の節を出し、戻したファイルを名指しする。停止（stop）と相談（consult）の判断にも同じ根拠を残す。
  - `keep`: 戻さない。仮説で加えた変更はそのまま残る。
- 黙って戻す挙動は無くした。v1.6 までの台帳と入力は `notify` として読む。戻すかどうかの判断は変えていないので、変わるのは「伝えること」と「記録すること」だけである。
- 評価ホスト: `--rollback notify|keep`（既定 notify。keep のときだけ variant に `/RB-keep`）。

試験: `test/scenario/rollback.test.ts`（keep は戻さず何も出さない、notify は戻して記録し、次の試行までの要求で名指しする、protective で損傷の兆候がなければ戻さない、旧入力は notify として読む）。

## b. 試行の判定の表示を反証の条件に基づかせる

問題: 実行した試行の「判定」は `outcome`（状態が予測どおりで、判定層の照合が低くないこと）だけで決まっていた。道具が ok を返せば、`refutedIf` に当たる観測が出ていても「予測どおり」と表示していた。

変更:

- `conditions.verdictLabel`: `"refutation" | "status"`（既定 `"refutation"`）。規則層が数える `outcome` は変えない。変わるのは表示だけである。
  - `refutation`: 状態が予測と違えば「予測と違う（状態が予測と違う）」。状態が合っていれば `refutedIf` を観測と突き合わせ、「反証の条件に当たった」か「当たらなかった」を示す。機械で判定できない書き方のとき、または `refutedIf` が無いときは「未判定」とする。ただし判定層の照合で失敗になった試行は「予測と違う（観測の照合）」とする。道具の状態だけで「予測どおり」と表示することはない。
  - `status`: v1.6 の表示（「予測どおり」「予測と違う/失敗」）。以前の実行を再現するために残した。
- 機械で判定できる `refutedIf` の文法は `status:ok`、`status:error`、`contains:"…"`、`not_contains:"…"` で、`||` で並べるとどれか一つが真なら反証とみなす（`src/domains/rules/refutation.ts`）。
  - 探す文字列は、観測の各文字列値と観測の JSON 表記の両方から探す。生成器が見ている観測は JSON 表記なので、`"output":"41"` のように JSON の形で書いても照合できる。hz11u では、値の文字列だけを探していたために反証と誤判定した例があった。
  - 引用符の中の `||` は区切りにしない。文字列は JSON 文字列のエスケープ（`\"`、`\\`、`\n`、`\u…`）として解く。末尾に区切りの `||` だけが残る書き方は自由記述として扱う。
- `prediction: "falsifiable"` かつ `refutation` のとき、提案の依頼で文法を説明する。
- 依存: generation が rules（refutation）を使うので、`scripts/domains.ts` に generation → rules を足した。rules は ledger にだけ依存するので循環は無い。
- 評価ホスト: `--verdict-label refutation|status`（既定 refutation。status のときだけ variant に `/VL-status`）。

試験: `test/scenario/verdict.test.ts`（文法、JSON 表記での照合、区切りとエスケープ、既定値、道具の状態だけで「予測どおり」と出ないこと、status の旧表示、提案の要求での表示と文法の説明）。

## d. 範囲の拡大（scope_growth）を課題のファイルの広がりだけで数える

問題: `scope_growth` は、試行ごとの `filesTouched`（仮説の checkpoint からの累積）の件数が、末尾で何回続けて増えたかを数えていた。hz11u では、読むだけの試行が 8 回続いたあと、`scratch/` に調べ用のスクリプトと出力を作る run が 3 回続いて累積件数が 0→2→4→5 と増え、兆候が出て一段上へ戻された。課題のファイルは何も変えていなかった。

変更（`src/domains/rules/checks.ts` の `scopeGrowth`）:

- 数えるのは、作業領域を変える試行のうち、その仮説の中で前の試行までに変えていなかった課題のファイルを新たに変えた試行が、末尾で何回続いたかである。累積の件数そのものは見ない。
- 読むだけの試行（道具が作業領域を変えず、新しく変わったファイルも無い）は飛ばし、連続を伸ばしも切りもしない。作業領域を変える試行が新しい課題のファイルを足さなかったときは、連続が切れる。
- `policy.signals.scratchDirs`（既定 `["scratch", "notes", "tmp", "__pycache__"]`）のどれかをパスの一部に含むファイルは、課題のファイルとして数えない。生成器にも、提案の依頼でこれらのディレクトリにメモや一時スクリプトを置くよう伝える（作業領域を変える道具があるときだけ）。
- 閾値は従来の `signals.scopeGrowth` のまま。新しいファイルを足す試行が N 回続けば、従来と同じ N で兆候が出る。

試験: `src/domains/rules/test/rules.test.ts` の「scope growth counts task files only」（hz11u と同じ並び＝読むだけ 11 回と scratch のファイルでは出ない、間に読みを挟んだ本当の広がりでは出る、何も足さない書き込みで連続が切れる、scratch のディレクトリは policy で決まる）。

## e. 知見の台帳と、自己評価・申告の食い違い

問題: hz11u の追求では、生成器は知見を一件も記録しなかった。それでいて、部品の自己評価には「定義を知見に記録した」と書いていた。台帳が空のままでも、規則層は何も言わなかった。

変更:

- 規則（`src/domains/rules/checks.ts` の `unrecordedFindingRefs`）: `conditions.findings` が off でなく、規則層が有効なとき、提案が台帳にない F番号を引用していたら `finding_not_recorded` で拒否する。見る先は二つある。
  - 構造化された参照（`uses`、`refute`）。
  - message・自己評価（evidence / next）・受入条件ごとの判断（where）の中の F番号。F番号はホストが振る ID なので、これは構造の照合であり、文の意味を読むものではない。
  - 同じ提案の findings に書いた知見は、照合の前に台帳へ入るので、その番号は引用できる。
- 促し（`src/domains/generation/prompts.ts`）: 毎手に知見を求めるほど重くはしない。
  - 提案の「知見の記録」に一文足した。あとで使う事実（定義・数値・原因の特定・反例）が分かる観測を得たら次の一手の findings に残すこと、知見に触れるときは F番号で引用すること、台帳にない番号は受け付けないこと。
  - 知見の一覧が空のときは「（まだありません。実行した試行 N 回）」と表示する。
  - 知見（行き止まりを除く）が 0 件のまま試行が 5 回以上実行されたら、方針と仮説の要求に「知見: 0 件（実行した試行 N 回のあと）…」の一行を出す。
- 文の中の「知見」という語を探して判定することはしない（語句辞書を足さない原則）。番号なしで「知見に記録した」と書く場合は、促しと「まだありません」の表示で抑える。

試験: `test/scenario/findings-consistency.test.ts`（番号の抽出と照合、台帳にない番号を引用する step back は拒否され、記録したうえでの引用は通る、findings off では何もしない、5 回のあとの促しと提案の表示）。

## f. 観測の切り詰め

問題: 試行の観測は、提案の要求では JSON 表記で 1800 字（`600 × 3`）、仮説の要求では 900 字で切っていた。直前の観測も例外ではなかった。切ったことは「この一覧での表示はここまで」としか示さず、全体の長さも続きを読む方法も分からなかった。hz11u では、76 件の資料一覧（list_sources）が途中で切れた。

変更:

- `policy.observation`: `{ latestChars, olderChars }`（既定 `{ 8000, 1800 }`）。最後に実行した試行の観測は `latestChars` まで、それ以外は `olderChars` まで表示する（仮説の要求の「直近の試行」は従来どおり半分）。台帳には観測を全部残す。切るのは要求の中だけである。
- 切ったときは「観測は全 N 字のうち先頭 M 字だけ表示」と書き、続きの読み方も示す。入力 schema に `offset` と `limit` を持つ道具なら「offset / limit で続きを読めます」、そうでなければ「範囲や件数を絞って呼び直すか、結果をファイルに書いて分けて読んでください」。
- 評価の道具で、読む系統の道具に一部ずつ読む方法を付けた。
  - 群D の `read_file`: `offset` / `limit`（行）。`lines` と `offset` を返す。
  - horizon-10a の `list_sources`: `offset` / `limit`（件。既定 30、最大 100）。`total` と `next_offset` を返す。
  - `fetch_page`: `offset` / `limit`（文字。既定かつ最大 30000）。`total_chars` と `next_offset` を返す。
  - horizon-10e の `read_file` には、もともと `offset` / `limit` がある。
  - いずれも指紋の対象に offset / limit を含めた。
  - 一部ずつ読む欄（total・offset・next_offset など）は本文や一覧より前に置く。観測が切られても欄は見える。

試験: `test/scenario/observation.test.ts`（policy の既定値、最新は 8000 字・古いものは 1800 字で、それぞれ全長と続きの読み方を示す、短い観測には注記を付けない）、`eval/tools/test/code.test.ts`（read_file の offset / limit）、`eval/tasks/e/test/horizon10a-adversarial.test.ts`（list_sources と fetch_page を一部ずつ読む）。
