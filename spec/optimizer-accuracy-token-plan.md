## 1. 比較の準備と状態表示

### 比較ランナーと記録

1. [ランナー](../examples/optimizer/run.ts)の方式選択と採点・記録処理を再利用し、候補の状態と計測範囲の伝え方だけを変えたOptimizer同士の比較を追加する。対照は現行の応答と指示を使う。両方式に自動採用を適用し、同じ校正結果と初期コードを別々の作業領域に渡す。既存の `compare` と `compare-selection` は、それぞれD0との比較と手動採用との比較に使う。
2. 比較条件、方式、実行順、コードの版、モデルと推論設定を `campaign.json` に残し、試行ごとの結果と集計を `result.json` と `summary.json` に残す。固定応答で現行の結果と計測回数を採取し、変更後も同じ候補・測定値に同じ採用・受入判定が出ることを確認する。既存の再開経路では、記録された方式と計測条件を照合する。
3. [使用量メーター](../standalone/usage.ts)を全試行のトークンの集計元とし、追求台帳の試行・推論・検証記録を経路の診断に使う。最初の基準版復元が確定した後の呼び出し数、同じ版で失敗済みの検証に対する再申告と `unchanged_failed_claim` による拒否、最初の相対計測が確定した後のトークンを記録する。復元や計測がなかった試行は該当なしとして別に示す。

### 既存の応答で版と根拠を伝える

変更は [課題アダプター](../eval/optimizer/task.ts)、[課題の入力定義](../examples/optimizer/fixtures.ts)、比較ランナーに置く。版の判定は [候補台帳](../eval/optimizer/candidates.ts)と現行ファイルのダイジェストから導く。台帳の `initial` は比較基準版を指し、課題開始時に作業領域へ置く初期ファイルとは別の版になりうる。台帳の `best` は比較に使う保存版で、初期状態では比較基準版を指す。`best` が比較基準版から更新された時点で、採用済みの改善版があると示す。計測規模は入力を生成した値を使い、規模が提供されない課題では省略する。

| 応答 | 追加する情報 |
| --- | --- |
| `read_candidate` | 現行版が比較基準版か、改善版が採用済みか、現行版が比較に使う保存版と一致するか。既存の `matches` は互換用に残す。 |
| `restore_best` | 実際に戻した版が比較基準版か採用済み改善版か。 |
| `measure_candidate` | 比較対象の2版、相対計測の操作数と分布、採用結果。記録を再利用するときは元の計測の版と範囲を示し、同一版で計測を省略した場合は新規計測なしと示す。過去の採用結果と現在の保存版を区別する。 |
| 開発用の受入結果 | 既存の `verification.targetVersion` にひも付けて、大規模入力の操作数、時間上限、速度検証の実施結果を示す。未実施の場合は、正しさの不合格や版の条件の未達など、実施を見送った理由を返す。 |

変更版の課題指示では、比較基準版に一致した場合は版の受入条件が未達であることと、相対計測と大規模の受入が別の根拠であることを短く示す。たとえば区間更新で不採用後に復元した場合、1,900操作の相対計測は不採用になった候補と比較基準版の記録であり、復元した版の36,000操作の速度検証は未実施と分かるようにする。受入結果を表示する際は現行版と `targetVersion` を照合し、以前の版の結果はその版の記録として扱う。速度検証の記録がない場合と、実施して不合格だった場合は区別する。

採用閾値、予算、隔離環境、開発用の受入条件、独立監査、公開条件、追求ループは現行の契約を使う。状態表示のために新たな計測を起動せず、独立監査の入力や結果は探索に渡さない。候補の修正、仮説の更新、継続・部分終了の判断はLLMに委ねる。

### 実モデルでの予備比較

- 一括訂正 `bulk-snapshots`、配送網 `inventory-branches`、区間更新 `range-moments` を各2反復、各反復2方式の計12枠で比較する。反復ごとに3課題を1組として実行し、各課題の2回目は順番を反転する。過去の比較と同じResponses APIの `gpt-6-luna / medium` を使う想定とし、実行版、接続方式、同じペアの校正・入力、初期コード、予算を事前に固定する。並行実行による計測の干渉を避けるため、同じLinux環境で順に実行する。
- 各枠はモデル17回、道具20回、計測6バッチ、480秒。各試行と実行グループに適用する既存の費用上限も記録する。独立監査は探索の時間枠と別に行い、両方式で同じ [監査予算の算定](../examples/optimizer/audit.ts)と3分布の未使用入力を使う。
- 校正でいずれかの分布のばらつきの閾値が比較基準版の実行時間の中央値の20%を超えた場合、ペア全体を未実行として記録する。校正の再試行は両方式のモデル呼び出し前に限り、実施条件と上限は比較前に決める。途中終了は結果として残し、同じ枠で再開した場合は再開前後の消費を合算する。
- 主指標は**独立監査に合格して公開された件数**と**実行した全試行のInput＋Output**。課題・反復・方式ごとに結果を残し、予定数、開始数、未実行数を併記する。開始後の未完了・時間切れ・中断は合格に数えず、その消費は集計に含める。環境要因で比較可能なペアが減った場合は、その範囲を示す。 [校正判定](../examples/optimizer/fixtures.ts)
- 補助指標は、合格1件あたりの総トークン、Input／Cached／Outputの内訳、同じ版の再読取り、基準版への復元後の消費と再申告。合格ゼロの比率は算出しない。使用量不明の呼び出しは件数を示し、既知の消費を下限として報告する。欠測で方式間の優劣を判断できない場合は節約の判定を保留する。
- 合格が増えて消費が減れば両指標の改善の兆候とする。片方が同等で片方が改善した場合は、その指標の改善として扱う。片方だけ改善してもう片方が悪化した場合は採用判断を保留し、課題別の経路を調べる。合格と消費が改善しても、基準版への復元後の呼び出しや再申告が減ったかを確認し、想定した効果が出たかを別に判断する。

予備比較は、固定応答の検証結果、12予定枠の結果、合格件数・総トークン・誤判断の経路を照合できる記録を残して終了する。環境や欠測で判定できない指標には再開条件を添える。採用判断は予備比較と分け、効果が見えた変更を新しい課題で再確認する。

## 2. 履歴の圧縮

両方式に現行Optimizerの状態表示と指示を使う。最初の比較では、`measure_candidate` の応答から全測定値の `result` だけを省く。採否、対象版・比較版、計測ID、分布ごとの根拠は既存の応答を使う。全測定値は既存の候補台帳で追跡できる。 [計測結果の要約](../eval/optimizer/benchmark.ts)

比較入口は `compare-measurement-summary`。Linuxの固定応答では、両方式が同じ版を公開し、台帳には全測定値が残った。全体検証は673件成功、3件スキップ、失敗0件。過去の現行Optimizerの計測応答4件では、直近の観測として提示する部分が1件あたり1,166〜2,602文字減った。 [比較コマンド](../examples/optimizer/README.md) · [Linux検証ログ](../artifacts/optimizer-measurement-summary-20261112/verify-linux.log) · [保存済み応答の表示量比較](../artifacts/optimizer-measurement-summary-20261112/archived-output-sizes.json)

実モデルでは12予定枠のうち4枠を実行した。4ペア8枠は再校正でも現行の20%基準を超え、モデル呼び出し前に未実行となった。実行分では現行版が2件とも独立監査に合格して公開し、総トークンは138,943だった。圧縮版は2件とも `measure_candidate` を呼ぶ前に部分終了し、公開0件、総トークン33,159だった。使用量不明は0件。**圧縮した計測応答を受け取った実モデル試行が0件だったため、圧縮による合格率とトークン消費への効果は判定保留**とする。 [実験条件](../artifacts/optimizer-measurement-summary-20261112/protocol.json) · [12枠の集計](../artifacts/optimizer-measurement-summary-20261112/comparison-audit.json)

この施策を再検証する場合は、候補・履歴・計測結果を固定し、計測応答を受け取る時点から2方式を比較する。まず、その次の判断と入力トークンへの影響を測る。課題全体の合格率と総消費の評価は、校正が成立する環境での通し比較で行う。

モデルに送る入力の内訳を調べ、コード本文の再掲が大きい場合は、[進捗判断の入力](../src/domains/generation/productive.ts)で古い書き込み本文の再掲を減らす。現行版、直近の失敗、未達条件、未評価の試行番号と拒否理由を維持し、必要な現行コードは既存の `read_file` の範囲指定で読める。全測定値の省略とコード履歴の圧縮は順に試し、どちらで変化したか追跡する。

完了条件は、固定応答で編集・検査・復元・提出が通り、現行の比較対照に対して独立監査の合格件数を維持したうえで総トークンが減ること。再読取りと出力の増加が入力の削減を相殺していないか確認する。
