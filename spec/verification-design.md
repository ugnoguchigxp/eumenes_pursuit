# 完了の判断・採点の漏れ・予測の具体性・断念の期待値

作成日: 2026-10-20
状態: §1・§2・§3 は実装済み（2026-10-20）。§4 は persist-1 の結果を見て、予算の整合に差し替えた。

## 背景（math-6 の台帳から）

1. 完了の申告が 0 件。照合を通った 15 件はすべて、ホストが試行ごとに走らせた照合（隠れた採点を含む）が拾ったもの。生成層は自分が解き終えたことを判断していない。
2. 試行ごとの採点で通った補題が「採点で確認」の知見になり、`findings: verified` の生成層に見えていた。隠れた採点からの部分的な手がかりが漏れていた。
3. 予測の成否（ok / error）は 97% 当たるが、ほぼ常に ok と書くだけで情報がない。中身の照合（d1 の D3）が使えたのは 422 回中 34 回。
4. 断念は平均 4.9 回の試行、予算の 12% で起きる。

## 1. 照合の時機（`conditions.verifyOn`）

`conditions.verifyOn: "attempt" | "claim"`（既定 `"attempt"`。v1.2 までの動き）。

- `attempt`: 今までどおり、作業領域を変える試行のたびに照合する。
- `claim`: 照合は完了の申告（`done`）のときと、終わるときの最終の照合だけ。試行ごとの照合はしない。生成層が自分で「終わった」と判断しない限り完了しない。
- 規則層が off（E0）のときは、今までどおり照合しない。
- 指標: 申告の正しさ（申告のうち照合を通った割合）、照合を通る草稿があったのに申告しなかった件数（`claim` では最終の照合で分かる）。

## 2. 採点の漏れを塞ぐ

- 照合の結果から知見を作るのは、完了の申告のときの照合だけにする。試行ごとの照合と最終の照合からは作らない。
- 申告のときの照合の知見は、申告して不合格だった場合に、そこまでで通った補題を残すためのもの。採点基準の項目の名前と理由は、今までどおり返さない（通った・通らなかった基準の id だけ）。
- `findings: verified` の過去の結果（math-4〜6、persist-1）は、この漏れを含む条件として読む。results.md にその旨を書く。

## 3. 予測の具体性

- 道具の提案に `refutedIf`（何が観測されたら、この仮説が誤りか）を必須にする。空、または予測の文面と同じなら、規則層が `prediction_not_falsifiable` で拒否する。条件 `conditions.prediction: "status" | "falsifiable"`（既定 `"status"`）。
- 観測のあと、`refutedIf` に当たったかを生成層に問う代わりに、d1 の post の質問で判定し、当たったら仮説の行き止まりとして記録する（判定器が off のときは記録だけ）。
  - 実装は後回し。質問セットに問いを足すには LARM 側の版の更新が要る。今回は、`refutedIf` を台帳に残し、生成層の試行の履歴に「反証の条件」として示すところまで。
- 指標: 反証の条件に当たった試行の割合と、そのあと仮説を替えた割合。判定の実装までは、拒否の数と、通過・部分点の差だけを見る。

## 4. 断念の期待値（persist-1 の結果で差し替え）

persist-1 の自己評価の腕（D）では断念が 0 件で、未完の追求はすべて振り返りの `stop` で終わった。原因は一段上へ戻る予算（`budget.stepBacks` = 4）で、仮説を替えるたびに一段上へ戻るため、方針 2 つ目の途中で 5〜6 回に達し、`step_backs` の段上げで止まる。そのとき試行は 40 のうち 2〜12 回しか使っていない。断念の期待値は、効く場面がない。

代わりに、予算を互いに釣り合わせた `config/policy.v3.json` を使う。

- `budget.stepBacks` を 8 にする。方針 3 × 仮説 3 を回し切るのに要る数（9 − 1）。
- 他の値は v2 のまま。

以下の期待値の設計は、断念が再び多くなったときのために残す。

`conditions.selfCheck: "parts"` のとき、断念の提案に次の項目を足す。

- `remainingPlan`: 残りの予算で試せること。
- `successEstimate`: 続けた場合の見込み（0〜1）。

規則層は、予算（試行）の半分以上が残り、`successEstimate` が 0.1 以上なら、断念を一段上へ（`step_back`）に替える。見込みの数字は自己申告なので、記録して較正を見る（申告した見込みと、同じ課題の実際の通過率の比較）。

## 測り方

- persist-1 で効いた腕を土台にする。
- `verifyOn: claim` の基準線と、`claim` の上で 3・4 を一つずつ足した腕を比べる。
- 課題は π²（10 回）と ζ(3)（4 回）。群 A でも、`claim` で正しく止まれるかを確かめる。

## 実施（persist-2）

- 腕: D（attempt、persist-1 の土台の再走）、claim、claim ＋ policy v3、claim ＋ falsifiable。
- 場面に応じた指示（自己評価の指示を、一段上へ戻る・断念を考える場面でだけ出す）は、土台のプロンプトを変えるため、claim の効果と混ざる。persist-2 の後に、単独の腕で測る。

## 読み方の注意（実装後のレビューから）

- 試行ごとの照合から知見を作らなくなったのは、`attempt` でも同じ。persist-2 の腕 D（attempt）は、persist-1 の腕 D と厳密には同じ条件ではない。
- `claim` で仮説の試行予算が尽きたとき、最後の試行が予測どおりなら、一段上へ戻る前に一度だけ申告の機会を与える。それ以外の申告を選ばなかった場合は、今までどおり一段上へ戻る。
- 追求全体の予算（試行・時間・遷移）で止まったときは、最終の照合だけが走る。通っていれば、分析の「申告漏れ」に数える。
- 失敗した申告は、そのたびに採点器を呼ぶ。最悪で 1 追求あたり約 27 回。
- 規則層が off（E0）では `refutedIf` を強制しない。E0 と falsifiable は組み合わせない。
- analyze の `--depth` の「照合を通過」は、完了かつ照合の通過。結末の表の verified は最終の照合だけを見る。claim の腕では両者がずれることがある。
