# 知見（finding）の保持 設計

作成日: 2026-10-20
状態: 合意（2026-10-20）。採点はまとめて行う（補題ごとの採点の呼び出しは作らない）。未確認の知見を見せるかどうかは比較する。

## 問題

探索では、棄却すべき仮説と、残す価値のあるもの（補題・反例・観測・行き止まり）が同時に生まれる。今の pursuit はこれを分けて持てない。

- 仮説を閉じると、その下で得たものは履歴の文章（仮説の結果）に埋もれる。生成層には直近 6 試行と仮説の一行の結果しか渡らない。
- 作業領域を checkpoint に戻すと、書きかけの成果物も消える（policy `restore: "protective"` は応急処置。残すか消すかの二択）。
- math-2・math-3 の観測: Haiku は π² で正しい補題の一部まで書いてから、全体が不合格で仮説ごと捨て、次の仮説で一から書き直していた。

## 方針

台帳に「知見」を、仮説・試行とは別の記録として持つ。仮説を閉じても知見は残り、依存していた前提が崩れたときだけ無効になる。作業領域を戻しても、台帳の知見は消えない。

## 記録（migration `pursuit-0002-findings`、追記のみ）

| 項目 | 内容 |
| --- | --- |
| id, pursuit_id, seq | |
| kind | `lemma`（成り立つ部分的な主張）/ `counterexample` / `observation`（道具で得た事実）/ `dead_end`（この条件では進まなかった経路） |
| statement | 本文（構造化した文。モデルの生の応答は残さない原則のとおり、要約した主張だけ） |
| assurance | `exact` / `numeric` / `model`（照合済み）/ `unverified`（生成層の主張のみ） |
| source | 出どころの試行 id（ない場合は null） |
| scope | `pursuit`（前提なし）/ `strategy`（その方針の前提の上）/ `hypothesis`（その仮説の前提の上） |
| strategy_id, hypothesis_id | scope の参照 |
| status | `active` / `superseded`（前提の方針が閉じた）/ `refuted`（反駁された） |
| reason | superseded・refuted の理由 |

## 作られ方

1. **生成層の宣言（unverified）**: 提案の出力に `findings: [{kind, statement, scope}]` を足す（任意、1 回に 3 件まで）。観測を見たあとの次の提案で宣言する。照合されていないので `unverified`。
2. **ホストの記録（exact）**: 仮説を閉じるとき、ホストが `dead_end` を自動で残す（「仮説 X は、理由 Y で進まなかった」）。行き止まりを繰り返さないためで、事実の記録なので `exact`。
3. **道具の照合（exact / numeric）**: 道具の結果が知見を返せるようにする（`ToolOutcome.findings`、任意）。例: 厳密な計算・検算の結果（exact / numeric）、テストの結果（exact）。
4. **照合でまとめて得る（model）**: 採点は呼び出しを増やさず、1 回にまとめる。証明の採点の 1 回の中で、証明が「補題」として示した部分（見出し `補題` / `Lemma`）にも個別の合否を出させる。合格した補題を `model` の知見として残す。照合の結果は `AcceptancePort` から、`CriterionResult` に付けた `findings` として返す。
5. **反駁**: 生成層は提案で `refute: [{id, reason}]` を出せる。ホストの照合（exact）と矛盾した知見は、ホストが refuted にする。

## 一生

- 仮説を閉じる: scope=hypothesis の知見は active のまま残す（その仮説の下で得た補題も、別の仮説で使えることが多い）。表示には「閉じた仮説 H の下で得た」と付ける。
- 方針を見直す: scope=strategy の知見は superseded にする（消さない。振り返りには見せる）。
- dead_end は superseded にしない（同じ行き止まりを避けるため、追求の終わりまで見せる）。
- 作業領域の restore とは無関係（台帳にある）。

## 使われ方

- 方針・仮説・提案・振り返りのプロンプトに「## 知見」の欄を足す。active を確かさの強い順、新しい順に最大 20 件。各行に確かさと scope を付ける（例: `[lemma・model・仮説3] …`）。superseded と dead_end は別の欄。
- 判定器（d1）には渡さない（生成層の自己申告を判定器の入力にしない、plan §8.3）。渡すのは件数だけ（照合済み知見の数、行き止まりの数）。
- 照合済みの補題は、仮説を変えても再証明させない（プロンプトで「確かめ済みとして使ってよい」と示す）。unverified は「未確認」と明示する。

## 条件と測り方

- 条件の旗 `findings: "off" | "verified" | "all"` を足す。
  - `off`: 知見の仕組みなし（いまの E3）。
  - `verified`: 照合済みの知見と行き止まりだけをプロンプトに入れる（生成層の宣言は記録するが見せない）。
  - `all`: 生成層の未確認の宣言も「未確認」と明示して入れる。
  - `verified` と `all` の差で、未確認の主張を見せる効果（役立つか、誤りが残るか）を測る。
- 比較: math-3s（E3、知見なし、π²・ζ(3)、T0〜T3、各 3 回、採点 Sonnet）を基準線とし、`verified` と `all` で同じ構成を回す。
- 指標:
  - 解けた割合（照合済みの完了）、止めすぎ
  - 一段上へ戻したあとの回復率
  - 知見の件数（種類・確かさ別）、そのうち後の仮説で使われた件数。使われたかは、生成層が提案の `uses: [id]` で申告する（unverified の扱い）
  - 同じ行き止まりの繰り返し（新しい仮説が既存の dead_end と同じ指紋の試行で始まった回数）

## 契約への影響（host contract v1 → v1.1、追加のみ）

- migration `pursuit-0002-findings` の追加。
- `ToolOutcome.findings?`・`CriterionResult.findings?`（任意）、`Report.findings`（件数と照合済みの知見の一覧）。
- ContextStill への受け渡しに、照合済みの知見を加える。追求の中の知見は pursuit が持ち、追求をまたぐ蒸留は ContextStill が行う（plan §0 の役割分担のまま）。

## 範囲外（この設計ではしない）

- 追求をまたいだ知見の再利用（ContextStill の役割）。
- 知見の自動的な一般化・要約。
