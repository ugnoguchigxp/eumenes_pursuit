# Pursuitの進捗制御とEumenesの再現試験

対象はPursuit 0.0.6の `productive` モードと、Pursuitの作業木にある [Eumenesエミュレータ](../../../examples/eumenes/README.md)。Eumenesの稼働環境、vendor、共通推論枠、製品設定は変えていない。

## 元の43回から分かること

[前回の分析](../research-loop-2026-11-09/README.md)と[43回の時刻・使用量](../research-loop-2026-11-09/post-acquisition-43.csv)を参照。Eumenes vendorの採用記録は0.0.4、source commit `2b6af95044409b94ac6cfaef23db22db94d1e9ff`、ホスト契約1.11、migration 8。調査開始時のPursuit HEADとはソースが一致しなかった。今回の対照は前回作業の0.0.5を凍結したもので、歴史的実行そのものの再試行ではない。

## 原因と変更

道具の `ok` や予測一致を、受入条件に向けた前進と区別していなかった。残予算と未着手部分を理由にレビューや仮説の再設定へ戻り、前進につながる操作がなくても次の提案を求められた。子処理の待機中も、以前は結果の有無だけで追求全体を待機させていた。この構造はソースと固定試験で確認した。43回すべての原因を同定したという意味ではない。

変更版は毎回、何が分かったか・どの不足が解消されたか・次の作業が何を増やすかをLLMに判断させる。進捗は出典、試行、受入条件と対応付け、道具の成功と別に保存する。変化のない同じ操作は再実行できない。別の操作をしても成果が増えなければ、新しい制約・根拠・結論が開く経路か、保存・独立検証・相談へ進む。契約違反は理由を返して訂正を一度認め、状態が変わらないまま同じ違反を繰り返さない。

既知の入力で独立した取得と書込みは並行受付できる。次の検討に結果が必要なら、モデルを呼び直さずイベント待機に入る。独立した仕事がある場合は検討を継続し、結果は推論中でも受け入れる。古い操作案は実行せず、前提と結び付いた推論上の結論は保持する。書込みは一度に一つで、読戻しと最終検証は保存の確定後に行う。未完了時は根拠がある記述と未確認の範囲を分けて保存する。

## 試験条件と反復

先に部分・結合試験で、道具成功と進捗なしの分離、拒否された検索から指定URLへの切替え、出典の対応、保存と読戻し、待機のモデル呼出し0、実行中の判断と外部取得の重なり、取消、期限、再開、重複・遅延receiptを確認した。複数調査で推論枠を共有する試験は別に行い、枠を1に保った。本体比較には枠の競合を入れていない。

通し試験は同じ依頼、固定取得資料、上限、Eumenesの入力形式、gpt-6-luna（medium、同じ単独実行用設定）、独立検証を使用し、一調査ずつ実行した。Webの応答は固定資料。本番の検索サービス、ネットワーク、推論キュー、Scratch、Doclingの性能は測っていない。通常入力とキャッシュ入力は別。ホストが待機中に推論やI/Oが動くため、時間は合算しない。単回の比較なので、モデル応答時間の分散を推定していない。

| 検証中に見つかったこと | 対応 |
| --- | --- |
| モデルが受入条件ID欄に説明文を書き、初回の技術・博物館比較が停止した | 受入条件のIDを出力契約で選択できるようにした。早い停止を性能改善に含めない |
| 次の技術比較は合格したが9回・87.91秒。短いI/Oの完了で2件の判断が古くなった | 独立した取得と一件の保存を同時に受付。必要な結果が揃うまで有用な作業がない場合は、判断を再発行せず待機 |
| 博物館で保存の反証条件が欠け、拒否が受入条件の不足と混同されて停止した | 保存・読戻しを含む各操作の反証条件を要求。拒否や中断を手順上の制約の記録に使えるようにし、本文の根拠や最終検証には流用しない |

詳細な比較は [comparison.json](comparison.json)。`events.jsonl` と `audit.json` は各実行の出力先にある。コードを変更した途中試験の値は最終版の集計に混ぜない。

前版は判断を同期的に呼び、変更版は判断を非同期ジョブとして待つ。そのため、待機ログの合計は実行形態の違いを含む。約29→38ミリ秒はログ上で待機とジョブ実行が重ならなかった時間で、時刻の丸めや結果採用の処理も含む。実行可能な作業を取りこぼしていた時間は、このログからは判定できない。変更版の実モデル比較ではWeb・保存ジョブの実行中に開始したモデル呼出しは0回。重なりが生じる動作は遅延を制御した固定試験で確認した。[待機区間の集計方法](../../../eval/eumenes-comparison.py)・[計測値](comparison.json)

成果が増えない処理として追跡できた代表例は、変更版の一部取得不能。施設Aの根拠を試行4で保存し、試行5で読戻したあと、試行6で実質同じ回答を再保存し、試行7で試行予算による読戻し拒否が起きた。既存の部分結果から再保存を選んだモデル呼出しは24.59秒、拒否から復旧する次の呼出しは23.76秒。2呼出しは計48.36秒、最初の呼出しから再保存・読戻し完了までの区間は48.44秒だった。これらの呼出しには未完了の判断と復旧も含まれるため、48.44秒全体を削減可能な時間とは扱わない。前版の矛盾資料では、台帳にない知見の参照で拒否された1回に5.90秒かかった。[試行番号・判断・生ログ](comparison.json)

最後のWeb結果採用後の時間を両版合格の4条件に限ると、129.221→100.382秒、モデル呼出しは16→8回。6条件合計では取得不能と取得上限が伸び、同区間の時間は10.204秒増えた。独立検証や最終回答の生成もこの区間に含まれるため、Web後の全時間は停滞時間とは区別した。別の固定遅延の競合試験では共有推論枠1で枠待ちの累計が165.2→133.9ミリ秒だった。[実モデル比較](comparison.json)・[競合試験](contention.json)

実際のEumenesで観測された前回完了の技術比較は、MDNの公式資料からオフラインメモアプリ向けの保存方式を比較する依頼だった。Web取得後の1,298.544秒のうち、モデル呼出し876.736秒、ホストが計上した実行待機403.926秒。依頼全体のホスト待機は404.178秒だった。もう一方の実環境の依頼は東京国立博物館と国立科学博物館の公式資料を使う撮影規則比較。いずれも今回の固定資料とは入力・運用条件が異なる。元の43回については用途・成果の対応付けができず、意味上の停滞時間は算出できない。[前回の分析と実入力の所在](../research-loop-2026-11-09/README.md)・[取得後の43回](../research-loop-2026-11-09/post-acquisition-43.csv)

最後の差分点検で、判断のreceiptと方針・仮説・相談を同一トランザクションにした。各実行の途中でその実行のソースは変更していない。検索拒否設定の変更版はこの修正後、その他の変更版は修正前の凍結ソースで実行した。変更は採用時の原子性で、モデル設定、指示、操作内容、受入条件には変更がない。仮説更新のあった取得不能ケースに対応する境界は、保存失敗を挿入して失敗前後の台帳と再送を照合した。パッケージの全検証は589件合格・12件スキップ・0件失敗。

途中試行を含む実モデル検証の使用量台帳の既知額は0.11219716 USD。前回の0.0.5調査費用と区別している。

## 互換性と残る確認

既存入力は従来どおり。利用には `conditions.execution: "productive"`、migration 10、[ホスト契約1.13](../../host-contract-v1.md)への対応が必要。Eumenesの現行ホストは単数の待機に対応しているため、採用版だけ差し替えても新しい並行動作にはならない。

不要なポーリングと同一状態の待機判断の繰り返しは固定試験で0。依存結果が未着の時間、モデル・外部処理の実行時間、実ホストの共有枠待ちは残る。新しい意味上の成果の有無はLLMの判断で、完全には保証しない。モデルのキャッシュは測定したが、キャッシュ効果を本体とホストに分ける試験や、Eumenesに採用した後の実測は残る。
