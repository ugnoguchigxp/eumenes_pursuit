# Optimizerの取引合計 初回検証

[実装計画](../../optimizer-first-validation-plan.md) · Solver基準版 `82770cd`

Optimizerの課題アダプターを `eval/optimizer/` に実装した。既存の `productive`、台帳、予算、作業領域、受入検証を使う。候補のコードと計測記録は作業領域外のSQLiteに置き、計測結果の確定と最良版の更新を同じトランザクションで行う。中断時は直前に確定した最良版を保持する。 [課題アダプター](../../../eval/optimizer/task.ts) · [候補の保存](../../../eval/optimizer/candidates.ts)

## 部分と結合

- 部分テスト4件が通過。境界を含む既知の答えと、3分布×12シードで高速な参照計算を全件走査と照合した。別に計測順序、誤出力・タイムアウト・誤差内・別分布の悪化による昇格拒否を確認した。計測中の記録を残して台帳を開き直し、未確定の結果が昇格できず、中断分も予算に残ることを確認した。 [部分テスト](../../../eval/optimizer/benchmark.test.ts)
- 結合テスト2件が通過。固定応答で、正しく速い版の昇格、境界を壊した版の棄却、正しいが遅い版の棄却、プロセス側の台帳を開き直した後の復元を確認した。別の試験では計測中に取消を発生させ、開き直した後に同じ計測を自動再実行せず、最良版を読み戻せることを確認した。 [結合テスト](../../../eval/optimizer/task.test.ts)

## Linuxでの通し検証

DockerのLinux arm64環境で、Bun 1.4.4、Python 3.13.5、既存の `bwrap` による隔離実行を使用した。モデルには固定応答を使い、候補のPythonコードは実行した。開発用の正しさ検査では基準を満たす版と遅い版が各6/6で一致し、窓の境界を壊した版は1件で不一致となった。計測は正しさを通った版だけに行った。

| 3,000件の入力 | 初期版の中央値 | 採用候補の中央値 |
| --- | ---: | ---: |
| 通常の混在 | 126.99 ms | 10.58 ms |
| 少数利用者への集中 | 203.04 ms | 11.06 ms |
| 多数利用者への分散 | 129.94 ms | 10.73 ms |

正しいが遅い版は保存済みの最良版を更新しなかった。作業領域に遅い版を残した状態で、追求台帳と候補台帳を閉じて開き直した。最良版を復元し、現行ファイルと照合して完了した。さらに別シードの20万件の入力を各分布7回、計21回実行した。全出力が期待値と一致し、最長229.49 msで、すべて3秒以内だった。公開した `windowsum.py` のSHA-256は最良版および独立検証の対象版と一致した。 [通し検証の記録](../../../artifacts/optimizer-first-validation/fixed-20261111/result.json) · [公開候補](../../../artifacts/optimizer-first-validation/fixed-20261111/windowsum.py)

リポジトリ全体の `bun run verify` は643件通過、失敗0件、12件スキップ。Solver本体とEumenesサンプルはフリーズ版と一致した。 [全体検証ログ](../../../artifacts/optimizer-first-validation/verify.log)

再現は隔離実行が使えるLinuxで `bun eval/optimizer/fixed-check.ts <新しい出力先>`。実モデル12枠の比較は後続工程で行う。
