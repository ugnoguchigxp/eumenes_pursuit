## 仮説と変更箇所

報告保存ツールの説明に許可されるキーを明示すると、結論が確定した直後の初回保存で書式エラーが減る。入館端末の試行54とラベル工程の試行60は、3つの必須キーに契約外のキーを加えたため `invalid_report` で拒否された。直後の再提出は契約外のキーだけを除いた入力で、いずれも保存と最終照合に合格した。最初の報告でこの3キーに絞れたかを比較する。説明の不足がエラーの原因だったかは、この比較で検証する。 [根拠の試行と照合結果](history-audit.md#判断と待機の点検)

| 方式 | `submit_report` の説明 |
| --- | --- |
| A（現行） | 「報告書を保存する。decision は adopt（採用）または retain（現行維持）、failed は不合格地点IDの配列、gain は全地点合格なら {lower,upper}、不合格地点があれば null。」 |
| B（候補） | Aの末尾に「content のJSONに含めるキーは decision、failed、gain の3つだけ。」を追記する。 |

変更は評価用の `submit_report` の説明1箇所に限定する。元の `reportSchema`、保存処理、`verifyReport`、共通プロンプト、権限、予算、終了条件を両方式で共有する。既存のツール一覧から `proposalRequest` に説明が渡り、通常の試行処理が `text` を `content` に組み込む経路を使う。入力の書式と成果の妥当性は既存の検証で判定する。 [当時のツールと採点器](../../../artifacts/live-long-20261111/worktree/eval/tasks/terminal-study.ts) · [次の操作への指示](../../../src/domains/generation/prompts.ts) · [通常の試行処理](../../../src/domains/loop/attempt.ts)

### 単一判断の比較

入館端末とラベル工程は、保存済みの失敗入力と成功入力を採点器に通す再現確認に使う。以下の4件は採点専用とし、候補の調整に使わない。全件監査済みで、既存の報告と保留中の道具はない。固定応答で通常の操作を通して監査と台帳読取りを再現し、同じ状態から次の提案を取得する。ケースごとの状態と入力のハッシュを両方式で照合する。

| ID・課題 | 判断時点の観測 | 期待する報告 `decision / failed / gain` |
| --- | --- | --- |
| U1・搬入口の受付機 | S08が不合格。性能計測なし。 | `retain / ["S08"] / null` |
| U2・備品受渡し端末 | S17とS41が不合格。性能計測なし。 | `retain / ["S17","S41"] / null` |
| U3・荷物の仕分け手順 | 全地点合格。D1〜D5は2、3、2、3、2点、D6は未計測。 | `adopt / [] / {lower:12,upper:15}` |
| U4・貸出登録手順 | 全地点合格。D1〜D5は1、2、1、2、2点、D6は未計測。 | `retain / [] / {lower:8,upper:11}` |

各ケース・各方式3回、計24件。各回はU1→U4の順に進める。1回目と3回目はU1・U3をA→B、U2・U4をB→Aとし、2回目は各ペアの順を逆にする。並行数1、1件1モデル要求、応答期限120秒、全体の経過時間上限55分。各回答は別の作業領域で、最初の提案だけを通常の試行経路で採点する。

**主指標は初回提案で有効に保存できた件数（各方式12件中）**。書式検査で拒否された数を併記する。保存できても採用判断・不合格一覧・性能範囲が受入条件と合わなければ内容誤りとする。保存以外の操作、保存前の完了申告、APIエラー、未実行も全予定件数に含め、個別に集計する。モデル要求数、入力・出力トークン、時間、費用は実測値を保存する。

**通し比較に進む条件**は、全24件の有効な応答が揃い、Bの書式エラーがAより少なく、初回の有効な保存が増えること。必須監査に不合格がある群と、全件合格した群のいずれでも、有効な保存件数が下がらず、Bに内容誤りや保存前の完了申告がないことも求める。Aの書式エラーが0件なら、この標本では効果を測れなかったと記録して現行を維持する。

### 通し比較

採点用のU1〜U4と異なる2件を、両方式で各1回、計4件実行する。未監査から開始し、監査、必要な計測、保存、読戻し、独立照合を通す。

| ID・課題 | 実行時の観測 | 期待する完了 |
| --- | --- | --- |
| T1・回収ステーションの受付方式 | S14とS27が不合格。 | 全地点の監査を終え、性能計測なしで `retain`、`failed=["S14","S27"]`、`gain=null`。 |
| T2・発送前の照合手順 | 全地点合格。D1〜D6は2、2、3、2、2、1点。5条件のどの組合せでも採用可否が未確定。 | 6件目を計測し、合計12点で `adopt`、`failed=[]`、`gain={lower:12,upper:12}`。 |

**候補の採用条件**は、通し4件すべてで期待結果とホストの受入照合が揃い、Bの書式エラーによる再提出が合計で減ること。Bに根拠確定前の完了申告や新しい重複操作がなく、下記の固定応答による再開確認も通ることを求める。同点、回帰、未収録、費用不明があれば現行を維持し、ケース別に根拠を残す。結論の適用範囲は、この報告契約と試した条件に限る。

## 実行前の検証と記録

1. **部分検証**。過去2件の初回入力を `invalid_report`、余分なキーを除いた入力を保存・照合合格と確認する。さらに、書式に合う誤った結論や、必要な計測が残る状態の報告が独立照合で不合格になることを確認する。
2. **結合検証**。固定応答でAとBに同じ状態を渡し、モデル要求の差分が説明の一文だけであることを比較する。同一の有効な提案は両方式とも保存・読戻し・照合に進む。保存結果が確定した直後で中断する固定応答の試験では、再開後の追求IDが同じで、確定済みの保存が重複せず、連続実行と同じ検証結果になることを確認する。既存の `eval/test/runner-contract.test.ts` と `test/scenario/process-recovery.test.ts` も確認する。失敗時は実モデル比較を始めず、比較の準備と条件の一致を点検する。
3. **実モデルの比較**。単一判断、通し比較の順に実施する。実行ごとに `artifacts/report-submission-comparison/<実行名>/` を新設し、事前の `manifest.json` にハッシュ・設定・予定順・予算・採点条件、`results.jsonl` に各応答・判定・理由・使用量、`summary.md` に全予定件数の集計と進行・採用判断を保存する。通し比較のSQLite台帳と道具イベントも保持する。

第1段階の成果はこの比較計画の確定まで。比較用の入力生成と実行は第3段階で行う。
