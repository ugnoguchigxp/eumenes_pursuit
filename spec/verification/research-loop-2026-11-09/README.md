## 原因と仮説の区別

| 論点 | 観測・再現で分かったこと | 判断の範囲 |
| --- | --- | --- |
| 単一操作の粒度 | 提案は一つのtool/input。一括欄はなく外部Webは逐次。固定試験の取得後にも、既に全文を受け取った資料をsource_readする往復を観測 | 構造と新規試験では確認。当時43回の内訳は不明 |
| 証拠の継続 | proposalは現在の仮説の試行だけを表示し、前の仮説の本文はfindingsがなければ渡らない | 文脈上の欠落として部分試験で確認。過去実行への寄与量は未確定 |
| 再読・更新・見直しの循環 | 試験の初期版で追加本文なしの更新・見直しを観測。ただし後述の試験契約の不足が混在した | 最終比較と初期試行を分離。当時の検索語や局所操作を推定しない |
| 上限・例外で情報未反映 | `deferInTransaction`の受付例外はinvokeのエラー観測化を通らない。途中保存の機会を失う | 同一transactionでの失敗を固定試験で再現し、回復経路を検証 |
| 小操作と大きな入力 | 一手ごとのstateless呼出し。固定依頼が動的履歴の後ろにあり、成果物読戻しは重複表示 | 配置と重複を修正。cache効果は実測値でのみ評価 |
| ホストの待機 | 元4件に共通推論枠1の待機。新規試験にはEumenesのQueueがない | 既存待機を改善効果へ加算しない |

現行Eumenesのmodel wrapperは、coreの外でreport全文、sources索引、残りのモデル・外部・検索回数を毎回渡し、担当のbundle指示を付加する。この指示にも早期保存、同じ仮説での根拠反映、不明と矛盾、必要箇所だけの修正がある。したがってcoreのbudgetBlock不足を「Eumenesには残予算が見えていなかった」という原因へ拡張しない。本文全体がsources索引で渡されるわけでもない。当時の凍結指示全文は未取得であり、現行bundleと同一とは扱わない。今回の隔離比較はこのホストpacket・指示・推論枠を再現したものではない。

## 採用した変更

1. **指示の修正**。再読の前に解消する不足を示し、取得済み本文を再利用する。内容のある部分成果を根拠とともに保存し、その後の更新は新しい根拠・訂正・要求変更があるときに限る。同じpartialの言い換えや再読を進捗とせず、必須の根拠不足が残るpartialをdoneにしない。使える道具で埋められない不足は部品の詰まりとして扱い、部分成果を保存して相談・未完了終了を選ぶ。同じ仮説で進められる読取り→執筆→確認を、作業段階だけを理由にstep_backしない。どの資料が十分か、どこを読み直すか、いつ申告するかはLLMの判断のまま。
2. **情報の修正**。提案へ前の仮説の直近6件の観測を既存の文字数制限付きで渡す。件数超過は明示し、必要な箇所を読む既存道具へつなぐ。提案にも共通のbudgetBlockを渡す。ホストが`calls_left`を返さなければ残数を推定しない。
3. **入力の再利用**。固定の道具・依頼を動的履歴の前へ配置。最新の成果物の読戻し本文は一度だけ表示し、古いことの警告、元の試行と判定は残す。plan/hypothesizeでは本文を省略しない。
4. **受付失敗からの回復**。ホストの受付callback内の例外は全transactionをrollback後、`tool_reservation_failed`の拒否と提案使用量を一度記録する。invokeへ落とさず、再送しない。次に保存するか、別経路を選ぶか、partialで終えるかはLLMが決める。writer自体の障害・revision競合・無効な戻り値は引き続き例外。
5. **独立読取りをまとめて選ぶ**。提案の`following`に入力が既知で独立した読取りを最大5件追加できる。先頭を含めて許可・read only・残予算を検査し、最初の試行と後続計画を同じtransactionへ保存する。以降はモデルへ戻らず一件ずつ既存のattempt/defer/receiptを通す。各操作の予測・結果・出典は別の試行として残り、LLM使用量を重複記録しない。失敗・拒否・結果不明・状態変更・取消・期限で未送出の残りを破棄する。LLMが独立性を判断し、コードは出力を後続入力へ代入しない。独立性をコードで意味解析して保証する方式ではない。

4は外部受付の失敗という再現可能な実行上の不足に限定した変更。題材、検索語、文章の意味を判定する分岐は追加していない。受入条件、独立した検証、権限、予算、取消、期限、pending結果の一度だけの採用を維持する。既存の失敗試験は「例外が投げられる」から「拒否が保存される」に契約を更新し、外部受付0、invoke0、pending0、使用量1回、rollbackをより詳しく検査した。拒否を成功に変えた試験ではない。

**計画はまとめ、実行は直列とした。** 指示だけの比較では通常の呼出し数が安定して減らず、読取りごとのpropose往復が残ったため、保存済み計画を追加した。既存pending契約は単一操作で、Promise.allを足すだけでは予算予約、取消、再開、遅延結果の採用を保てない。外部Webの並列受付は追加せず、ホストとの接点を保ったまま提案の往復を減らす。当時43回の操作が不明なため、この変更だけで元の21分39秒を解消すると主張しない。

## 検証条件

部分→結合→全体の固定検証を実施。変更前verifyは556成功・12既存skip、変更後は570成功・12既存skip。計画と出典の個別保持、権限、仮説/全体予算、受付拒否、道具エラー、workspace変更、期限、保存後の再オープン、取消後結果、重複結果、忘却を確認した。関連31件も全て通過。従来の実プロセス強制終了による回復試験は維持し、新計画ではDB再オープンと同期実行の中断を追加した。新しい結果を採るために受入条件を緩めていない。

実モデル比較は`eval/research-loop.ts`で実施。保存済みgenerator/reviewer設定を使用し、同じ入力・モデル設定・作成した資料fixture・道具・予算・独立検証を使う。baseline/candidateソースを別々に凍結し、runner/source/inputのhashを記録する。before全件→after全件と一調査ずつ実行し、競合させない。意味上の正しさは独立文脈のモデル検証でありexactとはしない。出典IDの存在は機械検査する。

資料は**検証用の短い作成資料**であり、当日のMDNや博物館ページの完全なsnapshotではない。元依頼の比較観点に対応する課題だが、実Web再実行やEumenesの保存・通知を通す試験とは区別する。外部取得時間はfixture処理の実測であり、ネットワーク時間ではない。Eumenes待機は含まない。SQLite保存、道具内の保存処理、モデル時間はそれぞれ別に記録し、重なる計測を単純合算しない。

資料・下書き・workspaceの道具はfixtureのメモリ状態を使い、coreの計画・試行・観測・判断は永続SQLiteへ記録する。report.jsonはこの仮想workspaceの成果物で、Doclingや実際のEumenesの文書保存receiptを検査したものではない。モデル・推論effort・headroomは前後同一の保存済み設定、追求の試行上限60・壁時計30分・仮説ごと6・遷移1500も同一で、上限を使って早期打切りする比較ではない。

最初の比較では検証役へ保存receiptが不足し、保存済み下書きに「保存の証拠がない」と再修正を要求した。この試行は不採用。変更途中版で同じ失敗が続いたため停止し、送出済み1呼出しの予約は未確定のまま保持した。合否条件を緩和せず、実際の保存回数・読み戻し回数・保存先を前後両方へ追加し、最終比較をやり直した。途中版の成果と費用を最終版の改善へ混ぜない。

次の候補では通常比較で取得済み本文の再読が減った一方、資料欠落で同じpartialの更新と再読が増えた。保存を急がせる指示の副作用を疑い、停止して記録を保持した。更新の条件を新規根拠・訂正・要求変更に限定し、未達のpartialをdoneと申告しない指示へ変更した。

さらに詳細な試行台帳を調べ、試験の入出力がEumenesの契約と異なることが判明した。本文を`evidence`ではなく`id`で返し、claimsの出典IDにEumenesと同じ正規表現制約がなく、存在しない出典を持つ下書きも保存できた。これが引用不合格と再修正に混在していたため、初期試行をPursuitの速度や指示の因果評価には使わない。部分成果の更新増加を指示だけのせいと確定することも撤回する。

試験側の本文識別子、claimsの状態・ID形式・上限、保存時の出典存在検査、成果物の読み戻しのpathを既存ホストの契約へ合わせた。受入条件を緩めず、誤った引用は保存前に拒否する。その後はPursuit候補を変えず、前後とも修正した同一runnerで6条件を測り直す。停止した3呼出しは未確定予約を残し、0 token/0費用にはしていない。途中試行の件数・停止と完了の区別は[trial-history.json](trial-history.json)に保持する。

### 何が新しく分かり、回答がどう変わったか

- 通常比較: 二つの本文で対象項目を確認し、比較表と根拠、記載がない事項を保存した。技術比較は具体的な容量値等を推測せず、施設Bの自撮り棒も不明を維持。後のsource_readで新しい本文は増えなかったため、afterでは初回の全文を使った。
- 取得不能: beforeは本文1件の保持後も再取得・検索・再読・完了申告の棄却を経て相談した。afterは本文取得3→2、検索2→1、source_read2→1、下書き2→1、成果物再読7→2、棄却4→0。施設Aの確認済み事実と施設Bの未確認を保持し、部分成果を完了と申告する反復を減らした。gradeは前後各1回で、afterの未完了を確認した。
- 矛盾: 両本文の撮影可否の不一致を明示し、機材の禁止など一致する範囲と、改定案内の適用関係不明を分けた。新しい日付や優先順位を作らず、両方の出典を持つconflictingの主張を保持した。
- 取得上限: beforeは本文1件の後、下書き0回・grade0回で受付例外となった。afterは新規取得を追加せず、拒否1回を記録して本文1件の事実を下書き1回に保存し、成果物再読1回、独立grade1回を経て未完了終了した。この条件の時間と消費量の増加は、以前欠けていた保存・検証を行った費用であり、beforeの速い例外終了を同品質の成功と比べない。

[固定の複数追求性能](deterministic-performance.json)は1/2/4追求で別測定し、before最大p95 14.12ms、最初の指示修正後15.42ms、最終版14.68msで既存250ms以内。これは外部モデル遅延・Eumenesの枠待ちの測定ではない。

有料比較後には、破棄された後続計画も追跡できるよう最初の試行のprediction.followingへ宣言を残す監査情報を追加した。この情報の有無で生成器のpromptが一致する固定試験を通した。さらに再開までに道具が同名の書込みへ変わる失敗を固定試験で再現し、道具契約のdigestが変われば計画を破棄する境界検査を追加した。関連31件を通過。有料比較の道具は全件固定で、この追加境界に該当しないが、有料測定の凍結ソースと最終ソースは同一だと扱わずhashをprovenance.jsonに区別した。最新コードの全verify・固定性能・配布物検査を別に実施した。

## 互換性と残課題

- 道具の入力契約、開始入力、モデル・既存の試行上限値は変更していない。提案に後方互換のfollowingを追加し、migration 9で計画の保存列を追加した。旧提案はfollowing省略で従来通り、既存の保存入力から再開できる。新coreを起動する前に追加migrationの適用が必要。
- 受付callback例外時の動作は変更した。ホストは投げられる例外だけで拒否を検知せず、`rejected`を扱う必要がある。[ホスト契約](../../host-contract-v1.md)に追記。Eumenesでの新パッケージ採用と製品の通し検証は未実施。
- 指示は、強制終了直前にLLMへ戻れない場合まで成果物の更新を保証できない。原観測は既存台帳に残るが、ホストが最終下書きしか公開しない問題を、このリポジトリだけで解消したとは扱わない。取消時に追加推論・保存を強制しない。
- 当時の43回を厳密に評価するには、所有domainからの許可された限定exportが必要。操作・観測・出典・下書き版・受入判断・推論相関だけを対象とし、隠れた思考や生のpromptは不要。
- 複数追求の固定性能検証はverifyの1/2/4追求で別測定した。実Eumenesの枠1での新しい競合比較、実Webの変動と大きな本文の品質、一括受付・並列結果の契約は未検証。
