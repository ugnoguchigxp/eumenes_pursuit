# Solverの検証結果を次の判断につなぐ実装計画

2026-11-11 · 実装前 · 基準コミット `59d64a72cfc2ca44fd0bb1622942981e633e66b7`

Solverが仮説を立て、操作を実行し、観測を検証して、次の操作または終了を選ぶ。今回の改善仮説は、**検証で使った根拠と判定できなかった理由を次の判断へ渡せば、同じ成果物の再保存や不要な再取得を減らし、独立照合に合格して完了する仕事を増やせる**、というもの。長期開発計画の第2段階で点検した履歴を、第3段階の比較に使う。 [長期開発計画](long-term-pursuit-plan.md)

## 比較の起点

- **50区画の調査。** 先行試行では、報告に50区画分の根拠があったが、採点に渡った台帳の抜粋は18〜20区画分で未完了になった。後続の順序検証では、Steerあり・なしともに50区画の引用が一致し、台帳全文と現行Markdownの保存記録を使って完了した。各条件1回で、複数の変更の寄与は切り分けられない。先行試行は根拠欠落の再現に、後続の記録は正常系の期待値に使う。 [先行試行](../artifacts/steer-evaluator-20261111/summary.json) · [順序検証](../artifacts/steer-renewal-ordered-20261111/summary.json)
- **別担当の確認が必須の窓口案内。** 先行試行は実行済みレビューの記録が採点に届かず2回不合格になり、同じ操作の提案を拒否されて未完了になった。後続の試行ではレビューを1回呼び、保存・読戻し・受入検証まで完了した。レビューを実施した事実、レビュー対象の版、指摘が現行版で解消したかを確認するケースに使う。 [先行試行](../artifacts/evaluator-in-task-20261111/front-desk-refined/result.json) · [完了試行](../artifacts/evaluator-in-task-20261111/front-desk-final/result.json)
- **終了判断への指示追加。** E1Rでの固定状態比較は現行・候補とも23/24正答だった。今回は終了判断の一般指示を追加する案を見送り、採点時の根拠と未確認箇所が次の判断に届くかを比較する。 [比較結果](../artifacts/decision-comparison-20261111/summary.json)

## 初回実装の範囲

対象は `productive` とEumenes検証用ホスト。既存の `AcceptancePort`、SQLite台帳、進捗判断、非同期の操作予約・結果採用を使う。受入条件と合格判定は比較の両方式で共通とする。既存ホストの返却値と旧台帳は読める形を保つ。今回は新規エージェント、DBマイグレーション、受入条件の追加、本番導入を対象外とする。

| 段階 | 判断と記録 |
| --- | --- |
| 仮説 | 未解決の受入条件と、何が分かれば次の判断が変わるかをSolverが選ぶ。既存の進捗判断、操作予測、反証条件を使う。 |
| 実装 | 許可された最小の変更・取得・計測を行う。既存の操作ID、結果、成果物の版を使い、保存が確定してから依存する読戻しや検証へ進む。 |
| 検証 | 条件別の合否と確かさに加えて、検証対象の版、実際に採点側へ渡った根拠の参照、判定できなかった理由を記録する。 |
| 評価 | Solverが修正、根拠補完、検証のみの回復、別経路、待機、相談、部分終了を選ぶ。現行版で凍結済みの受入条件がすべて独立検証に合格したときに完了を確定する。 |

### 検証結果の情報と次の判断

| 観測された状態 | 次の判断に渡す情報と期待する行動 |
| --- | --- |
| 成果物が受入条件に不適合 | 条件ID、対象版、該当箇所、判断根拠。該当箇所を修正し、更新版を検証する。 |
| 採点に使える根拠が不足 | 必要だった資料と、その取得・提示の有無、切り詰めや版の状態。取得済みなら既存の資料を使う。未取得なら追加取得、相談、部分終了の可否を判断する。 |
| 検証の実行・受領に失敗 | 検証の実行状態と、成果物・操作の確定状態。現行の `reverify` が適用できる場合は検証だけを回復する。適用範囲外の状態は記録し、既存の終了手順へ進む。 |
| 判定理由が特定できない | 理由不明として元の結果を示す。旧台帳、複数原因が考えられる結果、情報が欠けた結果から原因を補作しない。 |

検証用ホストは実際に送った資料の参照・版・範囲と保存記録を保持する。レビューの記録には対象版と確認範囲を残す。過去版に対するレビューを実施した事実は保持し、現行版への合格はその版の独立照合で確定する。記録は既存の台帳と忘却の範囲に収め、共有ログには本文やプロンプトの全文を出さない。 [受入検証の契約](../src/contracts/ports.ts) · [検証用ホストの受入検証](../examples/eumenes/acceptance.ts)

## 作業順

1. **変更前の記録を固定する。** 現行コミットを固定し、同一の保存済み成果から、成果の誤り、採点側の根拠不足、検証失敗を再現する。古い実行ログは再現材料として使い、現行版の対照は同じ条件で採る。想定した挙動が再現しなければ、次の編集前に仮説を見直す。
2. **既存の検証結果を拡張する。** 検証用ホストが把握できる事実を、既存の検証記録に任意項目として残す。条件IDと合否の既存契約を維持し、通常の受入検証と再開で同じ記録を使う。理由が不明な結果や既存ホストの返却値も受け取れることを確認する。
3. **進捗判断に検証の情報を渡す。** `productiveRequest` の既存の検証履歴に、対象版・理由・根拠参照を加える。どの操作を選ぶかはLLMが判断する。課題名、語句、今回の事例だけに対応する製品分岐を設けない。 [進捗判断の入力](../src/domains/generation/productive.ts)
4. **記録と判断入力を比較する。** 両方式で同じ採点器と記録を使い、候補だけが追加情報を次の進捗判断で受け取る。採点側の資料選択、判定基準、重複抑止、予算配分はこの比較の共通条件とする。取得済みの根拠を渡し直す経路が不足している場合は、判断改善の効果と分けて記録する。
5. **次の変更を測定結果で決める。** 無関係な操作の後に同一採点入力で再検証する例が残れば、現行の照合基準と実際の採点入力を突き合わせ、再検証の同一性を別の比較で扱う。探索が終了作業の予算を使い切る例が残れば、保存・読戻し・照合に必要な残量の表示を別に試す。 [現行の再検証基準](../src/domains/loop/productive.ts)

## 検証順と期待結果

| 段階 | 確認すること |
| --- | --- |
| 部分 | 同じ報告で成果の誤り、根拠不足、タイムアウトを区別できる。取得済み資料の採点入力からの欠落と未取得を識別できる。旧形式の読込みが通り、理由なしの不合格や判定不能が合格に変わらない。 |
| 結合 | 保存後、レビュー結果の採用後、受入結果の記録後で中断する。再開後は確定済み操作を重複実行せず、旧版の判定を現行版に使わない。成果を変えず根拠が補われたケースは、再保存なしで再検証へ進める。同じ採点入力で失敗した判定の反復と、正当な待機中の余分なモデル呼出しを点検する。 |
| 通し | 固定応答で「不合格から修正して完了」「採点入力の不足から根拠を補って完了」「必須資料が取得できず部分終了」を通す。既存の `bun run verify` とビルドを実行する。通過後、利用可能な実モデル枠で固定状態の比較、続いて未使用課題の通し比較へ進む。 |

実モデル比較の開始前に、対照と候補のソース・設定、ケース、モデル、道具、採点器、試行順、反復数、費用・時間上限を固定する。50区画と窓口案内は再現用に使い、効果判定には課題内容や資料構成が異なる未使用ケースを使う。各ケースを両方式で同じ判断前状態から始め、順序を交互にし、作業領域を分ける。再開を含む枠は推論設定の一致も記録する。全予定を分母にして欠落・エラー・未実行を明記する。

## 採用条件と完了条件

- 主指標は**独立照合に合格し、完了状態まで到達した件数**。成果が正しくても完了申告に至らなかった件は別に集計する。解けないケースは、確認済みの成果と未達条件を残す部分終了を期待結果とする。
- 固定状態の比較で正しい次手が増え、未使用課題の通し比較で正しい完了が増えるか、正しい完了と適切な部分終了を維持したまま対象の手戻りが減れば採用候補とする。誤完了、旧版判定の流用、再開時の重複、成果品質の回帰がある候補は採用しない。再保存・再取得・再検証の件数、時間、モデル要求数、費用も並べる。効果が判別できなければ現行の判断入力を維持する。
- 作業完了には、部分・結合・通しの結果、比較の設定と全予定の結果、採否の根拠、変更差分の点検が必要。実モデル枠が確保できない場合は、決定的な試験の結果と実モデル比較の残作業を記録し、効果は未判定とする。比較結果は `spec/verification/long-term-pursuit/` から原記録に辿れるようにする。
