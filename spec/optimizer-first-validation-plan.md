# Optimizerの初回検証と実装計画

2026-11-11 · 固定応答による通し検証済み · 基準版 `82770cd` · [長期開発計画の第4段階](long-term-pursuit-plan.md#5段階の導入順) · [Solverのフリーズ記録](verification/long-term-pursuit/solver-freeze.md)

最初の課題は、**利用者ごとの直近1時間の取引合計を、出力の仕様を保って高速化すること**。既存の追求ループに計測と候補保存の道具をつなぎ、モデルが仮説・変更・検証を一件ずつ進める。計測済みの最良候補は作業中の版から独立して保持する。

[初回検証の結果](verification/long-term-pursuit/optimizer-first-validation.md)

## 課題と合格条件

既存の `hz10e-window-sums` の仕様と初期 `windowsum.py` を使う。初期実装は各取引について全件を走査する。変更対象は作業用コピーの `windowsum.py`。CLIは標準入力から取引を読み、入力順に整数を出力する。同じ利用者について `t - 3600 < t' <= t` を満たす取引を合計する。同時刻の全取引と負の金額を含む。既存の仕様と試験は固定する。 [課題登録](../eval/tasks/e/horizon-env.ts) · [入出力と性能の仕様](../eval/tasks/e/env-work/hz10e-window-sums/README.md) · [初期実装](../eval/tasks/e/env-work/hz10e-window-sums/windowsum.py)

| 検証 | 入力と判定 |
| --- | --- |
| 正しさ | 窓の端（3600秒差を除外、3599秒差を含む）、同時刻、入力順の乱れ、返金、複数利用者、単一行、全件同時刻を含める。小規模では仕様から独立に作った単純な参照計算と全出力を比較する。大規模の期待値を作る別の参照計算も、小規模のランダム入力で単純な計算と照合してから固定する。 |
| 速度 | 同じLinuxホストで、同じPython、入力、隔離環境を使い、CLIの起動・入力・計算・出力回収を含む壁時計時間をホスト側で測る。通常の混在、少数利用者への集中、多数利用者への分散の3分布を用意する。比較可能な中規模入力で初期版からの改善幅を測る。大規模では既存要件の20万件・1実行3秒以内を適用する。 |
| 最終成果 | 独立した未使用入力でも全出力が一致し、大規模で時間要件を満たす。計測した版、最終確認した版、公開した `windowsum.py` のダイジェストを一致させる。 |

開発入力はモデルに使わせ、最終検証は別シードで用意したホスト専用入力を使う。各分布の入力、期待値、生成器、実行環境と試行順を版またはダイジェストで固定する。期待値と検査器は候補の実行領域に置かない。既存課題の再利用なので、未使用なのは入力と分布ごとの検証セット。

## Optimizerに追加する処理

1. **正しさを先に検査する。** `check_candidate` は作業中の版をダイジェスト付きのスナップショットにし、開発用の検査を実行する。返すのは対象版、合否、失敗の分類、試行参照。検査後に編集された版には結果を流用できない。
2. **合格した版を計測する。** `measure_candidate` は同じ版の正しさの記録を必須とし、隔離した新しい作業コピーで実行する。中規模入力は初期版・速い参照実装で予備校正し、初期版を完測できるサイズを測定開始前に固定する。大規模の初期版が時間切れなら時間切れとして記録する。3秒を実測値として速度比に使うことは避ける。
3. **計測済みの最良候補を保持する。** ホストが候補版、検査版、計測条件、全測定値、基準版をひも付ける。全ての正しさ検査と中規模計測に成功し、現在の最良候補に対して同じ入力の比較で測定のばらつきを超えて速くなった版を保存する。同等、悪化、誤出力、時間切れ、取消では最良候補を更新しない。最良候補は変更不可のコピーとして作業領域の外に保存し、選定記録の更新は一度だけ行う。`restore_best` はモデルが指示したときに、その版を作業領域に戻す書込み操作とする。
4. **終端で検証する。** モデルが完了を選んだときは、作業中の提出版が計測済みの最良候補と一致することを確かめ、凍結した開発用の受入条件を照合する。実験上の「正しい完了」は、提出後に未使用入力で行う独立検証まで通った場合に数える。未使用入力の結果は次の探索に戻さない。予算切れ・取消・閾値未達でも、既存の終了状態と理由を保ち、最後に検証済みだった候補があれば版と確認範囲を添えて部分成果に残す。

同じ版と計測条件の組を識別し、再開時は確定済みの結果を読み戻す。計測開始を記録してから実行し、結果が確定する前に中断した場合は未判定として扱う。中断分は予算に含め、再開時に同じ処理を自動で再実行しない。再開後にモデルが明示的な再計測を選んだ場合は、既存の重複・予算の契約を適用する。記録は結果と最良候補の参照を同じ更新で確定し、途中で終了しても直前の確定済み版を参照できるようにする。

## 計測手順と比較

- **計測の順序。** Linuxの `bwrap`・`prlimit` と実際のPython起動を事前確認する。ホストを専有し、同時に複数のベンチマークを走らせない。初期版と速い参照実装をそれぞれ同一版どうしで測り、測定のばらつきを求める。候補と基準は各入力で1回ずつ予熱後、順序を交互に7組測る。全値と組ごとの差の中央値を保存する。候補の昇格は、6組以上で速く、差の中央値が同一版比較のばらつきの95パーセンタイルを超え、他の分布にそのばらつきを超える悪化がないことを初回の基準案とする。主指標は最初に固定した通常分布の中規模入力とし、集中・分散は回帰検査に使う。最終の20万件入力では計測した7回すべてに3秒の上限を適用する。ばらつきが大きく判定できない測定は未判定にする。
- **同じ予算で対比較。** 対照は既存の `productive` に同じ編集・検査・計測を渡し、候補の保持は作業領域内でモデルが行う。Optimizer側は同じループに最良候補の保存と復元を加える。中規模の測定データと初期版の結果は双方が利用できる。対照ではモデルが保存した比較版を指定でき、Optimizerではホストが保持する最良版を比較相手に使う。どちらも最終提出した版を同じ検査器で照合する。3分布の未使用検証セット×各2回×2方式で計12枠。ペア内で方式の順を交互にし、独立した作業領域を用意する。最初の予算案は1枠あたりモデル17回・道具20回・計測6バッチ・480秒。最終の未使用入力による独立検証には双方共通の60秒を別に確保する。計測1バッチは、候補と比較版の予熱と7組の計測を含む。予算・モデル設定・実行版は固定応答の通し後、実モデル比較の前に凍結する。
- **優先する指標。** まず成果物の品質を確認し、対照が正しく完了したペアでの劣化、誤完了、検証済み候補の消失を一件ずつ点検する。次に、初期版からの速度改善が別シードで再現するか、対照と比べて時間要件を満たす最終成果が得られるかを見る。試行数、失敗後の復元、再計測、壁時計時間、Input／Cached／Outputは別々に報告する。時間切れ、未実行、計測環境エラーも予定枠に残す。

## 実装順と段階ごとの受入条件

| 段階 | 作業と通過条件 |
| --- | --- |
| 部分 | 参照計算、入力の分離、計測の集計、最良候補の更新を個別に検証する。正しく速い候補は昇格し、誤出力の高速候補、誤差内の候補、別版の検査結果、タイムアウトは昇格しない。負例には窓の端と同時刻を崩した実装を入れる。 |
| 結合 | 既存ランナーと固定応答で、初期版→正しく速い版→速いが誤出力の版→悪化した版→復元→提出を通す。計測後・更新直前の中断と再開、結果の二重採用、古い版の提出、検査ファイルの変更を試す。成果物・検証・計測のダイジェストが一致し、どの試行でも検証済み候補を失わないことを確認する。 |
| 通し | 隔離実行できるLinuxで、実入力を使う固定応答の一連の実行を先に通す。その後、設定を凍結して実モデルで12枠を比較する。隔離実行または計測の校正が成立しない場合は、その段階の結果を未判定として記録する。 |

次ラウンドの実行入口は `eval/optimizer/` に置く。部分・結合は `bun test eval/optimizer`、通しの固定応答と実モデル比較は同ディレクトリの比較ランナーから起動する。計測条件、台帳、公開候補、各試行の値、利用量と集計は `artifacts/optimizer-first-validation/` に保存する。

実装の完了条件は、両方式の全予定枠と成果物の照合結果を残し、同じ予算で速度改善と最良候補の保持を再現できるか判断できること。品質に回帰が出た場合はまず原因を特定する。対照も同程度の成果を出した場合は、候補保存の追加が効いた場面を実行記録で確認する。最良候補を失う問題が再現しない場合は、実行方式を増やす根拠が得られるまで逐次改善のまま扱う。
