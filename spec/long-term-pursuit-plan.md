# Eumenes Pursuit 長期開発計画

2026-11-11 · 第1段階完了、成果物の事後レビューを検証済み

第1段階の成果は [履歴の点検表](verification/long-term-pursuit/history-audit.md) と [報告の初回保存を比較する計画](verification/long-term-pursuit/report-submission-comparison.md)。第2段階は、導入済みの成果物レビューと既存の実行記録を使い、判断の根拠をどこまで検証できるか確かめる。

Solverは検証情報の引き継ぎまでを既定とし、改善をいったん凍結した。Astra Maxの提案、実モデル比較、再開時に残る検証は [Solverのフリーズ記録](verification/long-term-pursuit/solver-freeze.md) を参照。

## 目標と設計方針

Eumenes Pursuitは、受入条件のある目標を引き受け、仮説・実験・観測を積み重ね、根拠付きの成果を返す独立したライブラリを目指す。受入条件を満たした、仮説を棄却できた、再利用できる成果を保存した、という変化を進展として記録する。条件を満たせば終了し、中断時は確認済みの根拠と成果を残して、再開後の判断に使う。

既存の追求ループを最初の専門エージェントであるSolverと位置づける。SQLite台帳、モデルとツールの接続、予算、権限、状態遷移、再開、ホストによる受入検証を共通基盤として使う。進展の意味、仮説の妥当性、次に選ぶ行動はLLMが判断し、コードは権限・予算・検証契約と、外部操作や結果採用の重複防止を担う。共通化は、複数の専門エージェントで実際に必要になった責務から行う。公開APIと保存済みの追求の互換性を維持し、AgencyとCollaborationは今回の対象外とする。 [初期の研究計画](../plan.md) · [進展制御の設計](productive-loop-2026-11-09.md) · [ホスト接続契約](host-contract-v1.md)

| 評価軸 | 何を見るか |
| --- | --- |
| 成果品質 | 最終成果と途中成果の受入条件、根拠との一致、完了・部分終了の妥当性。 |
| 実行過程 | 重複操作、不要な継続、失敗後の回復、再開後の重複、モデル要求数、トークン、費用、時間。 |
| 判断品質 | その時点で得ていた観測・残予算・保留中の操作から、実際に選んだ操作が合理的だったか。 |

事実は台帳とホスト検証で照合する。観測の意味や判断の妥当性には根拠を付け、評価結果を軸ごとに残す。

## 5段階の導入順

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| **1. Solverの基準を固定する** | 直接解法（D0）・振り返り付き追求（E1R）・進展評価付き追求（`productive`）の保存済み比較を基準にする。台帳から判断場面を点検し、改善仮説を1件選んで比較計画を作る。 | 下記の点検表と比較計画が揃い、別の担当者が原記録と照合して比較を準備できる。 |
| **2. 履歴評価を独立させる** | 導入済みの成果物レビューを使い、保存済み履歴から判断時点の情報と採点に実際に渡った資料を読み取り専用で確認する。ホスト検証と点検済みの事例を基準にする。 | 正当な待機と停滞、部分終了と完了を区別し、成果物と実行過程への指摘をそれぞれ原記録まで辿れる。情報不足の判定を保留できる。評価は事後に行い、追求の動作への反映は別に検証する。 |
| **3. ハーネスの変更を一つずつ比較する** | 指示、判断に渡す情報、ツール説明などから一箇所を変更し、同じ課題・モデル・道具・予算・採点で現行と比較する。独立検証で採点できる比較はPursuit側で先行できる。 | 対象の問題が未使用課題でも減り、成果品質、終了判断、再開時の重複に回帰がない。効果が確認できなければ現行を維持し、観測から仮説を見直す。 |
| **4. Optimizerを一種類試す** | 測定可能な指標を持つ課題で、正しさの検査と性能計測を分けて逐次改善を試す。検証済みの最良候補を保持する。 | 同じ予算で性能改善を再現でき、Solverとの共通部分とOptimizer固有の計測・採用・停止条件を実例から示せる。候補の枝分かれに価値が見えた場合に、逐次改善とBest-Firstなどを比較する。 |
| **5. Harness Engineerへ進める** | 段階3で再現できた問題の診断、変更候補の生成、比較を隔離環境で自動化する。評価器、権限、採用判定、ロールバックは候補の変更範囲から外す。 | 未使用課題で改善が再現し、候補ごとの効果、適用条件、採用・棄却の根拠を再確認できる。探索予算の配分は候補数や評価費用が制約になった時点で試す。 |

第4段階の最初の課題、Solverとの再利用境界、実装順は [Optimizerの初回検証と実装計画](optimizer-first-validation-plan.md) にまとめた。

Optimizerは対象システムの指標を改善する。Harness EngineerはPursuit自身の実行能力を改善する。その他の専門エージェントは、既存Solverで不足する能力と、それを独立に評価できる課題が揃った時点で検討する。

## 第2段階に引き継ぐ検証

Evaluator 0.1.0は、Pursuitの検証用環境に接続済み。保存済み報告と引用本文を使った事後レビューは、資料が揃う課題と必須資料が欠ける課題の両方で動作を確認した。実行過程については、Pursuitの台帳とイベントを根拠に評価する。Evaluatorに履歴を渡す範囲は、既存事例で必要な証拠を確認してから決める。 [事後レビューの実行手順と範囲](../examples/eumenes/README.md#保存した報告の事後レビューevaluator)

1. **判断時点の記録を照合する。** 第1段階の点検済み事例から、直前までに採用された観測、保留中の操作、適用された上限、実際の判断を取り出す。待機・停滞・部分終了の評価に使った試行やイベントを特定し、記録から判断できない箇所は保留する。
2. **成果物と採点時の証拠を照合する。** 50区画課題の記録で、実際に保存されたMarkdown、取得済みの資料、採点時に渡った資料を照合する。報告の欠落、採点側の証拠不足、実行過程への指摘を区別し、指摘が操作の有無に言及する場合は実行ログと照らす。 [検証事例と期待する判定](verification/long-term-pursuit/history-audit.md#第2段階に使う事後レビューの事例)
3. **進行中の修正結果を取り込む。** 50区画課題での仮説数上限からの回復と、採点への資料・保存記録の受け渡しは、進行中の再検証結果を追記する。その際、完了状態、照合できた区画数、取得済み根拠の保存、Evaluatorの指摘と実行ログの一致を確認する。報告の初回保存を改善する比較は、第1段階で確定した計画で扱う。

## 第1段階の作業範囲

保存済みの履歴を読み取り専用で点検し、**履歴の点検表**と**改善仮説1件の比較計画**を作る。点検表と比較計画は `spec/verification/long-term-pursuit/` に置き、元の台帳や実行ログは既存の実行ディレクトリを参照する。新規の実モデル実行と比較候補の実装は第3段階で扱う。

### 1. 履歴の点検表を作る

既存の比較結果から、方式ごとの期待結果、受入検証、道具呼出数、モデル要求数、時間、費用を転記する。実行名、ソースと設定の識別子、モデル、課題、予算を原記録から確認する。既存比較は3課題を各方式1回ずつ実行したもので、方式間の差は点検対象を探す材料として使う。D0の行動は直接解法の実行記録、E1Rと `productive` の行動はSQLite台帳を起点に辿る。 [比較の実行条件と結果](pursuit-baseline-2026-11-11.md)

| 点検する場面 | 対象と照合する証拠 |
| --- | --- |
| 正常な進展 | 共有キャッシュ調査の `productive`。新しい観測を受けた判断を一つ選び、根拠の試行番号と、その根拠が成果物で使われた箇所を照合する。 |
| 正当な待機 | `museum` の固定試験。最初の資料を取得した後、依存する別資料が到着するまでの区間を、道具の開始・到着時刻とモデル要求の記録で照合する。 |
| 進展のない反復 | 一部資料を取得できなかった11月9日の修正前の記録。試行4・6・8の保存内容と停止理由を見比べ、受入条件に関わる新しい根拠が増えたかを確認する。 |
| 根拠を残した部分終了 | 同じ取得不能ケースの修正後の記録。保存・読戻しと独立検証を辿り、出典の照合結果と回答の充足状況を記録する。 |
| 根拠確定後のやり直し | 11月11日の入館端末・ラベル工程の2実行。結論が確定した操作、初回の報告保存エラー、再提出、最終検証を順に照合する。 |

履歴の入口は [基準比較の履歴](pursuit-baseline-2026-11-11.md#評価と再開に使う履歴) と [部分終了の追試](verification/partial-finalization-2026-11-09.md) を使う。長時間課題のローカル原記録は `artifacts/live-long-20261111/evidence/` の各課題の `audit-events.jsonl`、集計は同実行の `summary.json` にある。台帳は `bun eval/trace.ts --ledger <台帳のパス> [追求IDまたは課題名]` で読み取り専用で開く。表示が省略された箇所は保存済みの試行、イベント、成果物を参照する。

**一行は一つの判断または一つの待機区間**とする。列は次のとおり。

| 列 | 記録する内容 |
| --- | --- |
| 実行と位置 | 実行名・課題・方式・追求ID、判断や試行の番号。待機は前後のイベント番号。 |
| 判断前に利用できた情報 | 目標と関係する受入条件、既知の観測と成果物の版、未確認事項、保留中の操作、残予算。 |
| 選んだ操作と理由 | 実際に採用した操作または待機・終了。記録に残る理由と、参照した根拠。 |
| 結果と進展 | 後で増えた観測や成果、失敗・拒否・待機の結果、受入条件ごとの照合結果。 |
| 評価と出典 | 当時の情報に照らした判断の評価、実行上の無駄や回復、原記録のパスと位置。確認できない項目は「記録なし」または「判定保留」。 |

**点検表の完了条件**

- 表に挙げた5種類の場面を記録し、根拠確定後のやり直しは2実行とも含める。全行で原記録の識別子と位置を辿れる。待機では開始と到着、部分終了では保存・読戻しと独立検証、反復では前後の内容を突き合わせている。
- 判断時に使えた情報と事後に判明した結果を区別している。モデルが述べた理由、ホスト検証の結果、点検者の評価をそれぞれ確認できる。
- 対象の問題を少なくとも1件、試行またはイベント番号で示している。既存の指示、ツール契約、再利用できる検証を確認し、観測した事実と原因の仮説を分けて比較計画へ引き継いでいる。

### 2. 改善仮説1件の比較計画を作る

**最初の候補は、根拠確定後の報告保存のやり直しを減らすこと。** 入館端末とラベル工程では、根拠が揃った後の初回保存が両方とも書式エラーになり、再提出は各1回だった。原記録では、入館端末で `auditedCount`・`auditedSites`・`rationale`、ラベル工程で `report` が契約外の項目として含まれていた。既存のツール説明は `decision`・`failed`・`gain` の意味を示し、検証器は余分な項目を拒否する。仮説は「許可されるキーがこの3つだけであることをツール説明に明示すると、初回保存の書式エラーが減る」とする。原因や効果は比較で確かめる。 [元の長時間課題の実行計画](../artifacts/live-long-20261111/plan.md)

| 固定する項目 | 比較計画に記載する内容 |
| --- | --- |
| 対照と候補 | 対照は現行の `submit_report` の説明。候補は同じ説明に「`content` のJSONに含めるキーは `decision`、`failed`、`gain` の3つだけ」を追記する。報告スキーマ、受入検証、目標、共通プロンプトは同一とする。 |
| 対象と回数 | 既存2件を再現確認に使う。採点用には、必須監査で不合格が出た状態と、全件合格して性能の範囲から結論が確定した状態を、未使用の課題から各2件用意する。両方式に同一の判断前状態を渡し、各状態・各方式3回、計24件を初回の比較とする。順序はペア内で交互にし、試行の作業領域は分ける。 |
| 採点と計測 | 最初に選んだ操作が有効な報告保存かを既存の書式検査と状態から判定する。書式エラー、内容の誤り、保存以外の操作、保存前の完了申告、APIエラーを記録し、全予定件数を分母に含める。モデル要求数、トークン、時間、費用も記録する。 |
| 採用の条件 | 未使用課題で書式エラーが減り、初回の有効な保存が増え、両方の状態で有効な保存の件数が低下しない。候補による新たな誤報告や早すぎる完了がなく、次の通し比較でも最終の受入結果を保ったまま再提出が減る。単一判断の比較は通し検証への進行判定に使う。 |

比較を実施するときは、まず固定入力で、契約に合う報告が通り、余分なキーは書式検査で、誤った結論は受入検証で拒否されることを点検する。結合検証では、同じ保存済み状態を両方式に渡し、ツール説明の一文だけが異なることを固定応答で確認する。その後に単一判断の比較を行い、進行条件を満たせば通し比較に進む。通し比較には、根拠が不足する状態から実行し、必要な計測を経て保存・読戻し・独立検証に進む未使用課題を含める。

**比較計画の完了条件**

- 対象の失敗と改善仮説が点検表の行から辿れ、変更する説明が一つに特定されている。元の契約と採点器をそのまま使える。
- 対照と候補の入力、実行版、対象の状態と期待結果、試行順と回数、共通の時間・費用上限、採点手順、結果の保存先を、実行前に固定できる形で記載している。採点用の課題は候補の調整に使った課題と分ける。
- 部分・結合・通しの期待結果、比較へ進む条件、現行を維持する条件が揃っている。既存履歴で候補の前提が崩れた場合は、変更を作る前に別の仮説1件へ入れ替え、その根拠を点検表に残す。

第1段階は、点検表を原記録と照合し、比較計画の条件を事前に点検できる状態で完了とする。比較の実施と採用判断は第3段階の成果とする。
