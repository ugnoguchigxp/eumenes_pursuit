# Fixes after hz11i (2026-10-22, e)

hz11i: both conditions 5/5, every task on its first claim. These are the follow-ups to the
responders' reports. Section numbers follow the request.

## 1. Role isolation of the responders' scratch (author tool, make_run_dirs_j.py)

Root cause: READY named one scratch dir, `<run>/work/`, for every role. In hz11i the grader
wrote work/grader-0001.json (pursuit) and work/verdict.json (direct); the reviewer's notes sat
next to the generator's scripts.

Change: each role has its own scratch:
- generator `<run>/work/gen/`;
- reviewer `<run>/work/rev/` (pursuit only);
- grader `<run>/grader/work/`.

READY names each role's own dir and puts the others off-limits. `<run>/grader/` was already
off-limits to the generator and reviewer.

Audit of hz11g/h/i (both conditions), with no evidence of cross-reading:
- The grader's files in work/ were all written after the generator's last response of the run. The
  grader is only called by water-ratio's (last task's) claim, which passed every time, so nothing
  came after it. Gaps: 15 s (g pursuit), 12 s (g direct), 14 s (h pursuit), 13 s (h direct), 18 s
  (i pursuit), 15 s (i direct).
- No generator or reviewer response names a grader file, verdict.json or grader/.
- The one hz11i reviewer response that names a generator file name (ref.py) got it from its own
  request, which quotes the attempt.

So the sharing was harmless in these runs, but it was a real hole and is closed for hz11j on.

## 2. Reviewer framing: routine step back or stall (core)

The reviewer system text said "You review a stalled pursuit". Every hz11i step back followed a
success. The text now says a step back is routine or a stall. The request carries 「## 戻った事情」,
which is 定例 when the generator stepped back right after an attempt that met its prediction (status
as predicted, outcome success, refutedIf not hit), and 行き詰まりの可能性 otherwise. The reviewer is
asked to write なし when no premise broke.

## 3. One tally in the review request (core)

The separate 「仮説N: 試行…、予測と違う/失敗…、拒否…」 lines are gone. The reviewed hypothesis's
line carries the one tally, now with 拒否, and closed hypotheses of the current strategy carry
their counts on their own history line.

## 4. Premise corrections after a review (core): implemented, as presentation

`change_strategy` already exists, but it asks for a strategy with a different core idea and costs
the strategy budget. That is the wrong tool for 「その段だけを直す」. With continue_strategy, a
non-empty brokenAssumption is now stored with the strategy id in the decision basis.
Every later request shows it under the strategy:
「［振り返りでの前提の修正（方針の文面より優先）: …］」 (last 3).

A brokenAssumption that is なし, or that opens by saying no premise broke, is not shown. In hz11i,
2 of the 4 reviews wrote 「壊れた前提はない。…」 and 2 named a real broken premise (「単一の段が根本原因だという前提は成り立たない」).

The ledger's plan text is not rewritten, and no budget or rule changes. This is cheap and
consistent with the rule that recorded text is append-only.

## 5. Findings promotion (core): not wired, documented

Promotion was not implemented. A passed claim says the acceptance criteria hold, not which of the
cited findings were true. A met prediction tests the hypothesis's prediction, not the findings it
cites. Promoting either would label unchecked claims 確認済み. A pursuit also ends at its passed
claim, so a promotion there would have no reader.

Only host-recorded findings (dead ends, 確定) and findings a check confirms on its own (graded
lemmas) are 確認済み. The findings block now says so in one sentence.

## 6. Probe observations shown as Python repr: not the harness

Both conditions render every observation, latest and older, through the same `observationText`
(JSON). The `('…', '54', '26')` tuples in hz11i direct black-box #19 are the stdout of the
responder's own Python script inside a JSON string. Nothing changes.

## 7. Task-wording ambiguities

- **sales-pipeline, 四捨五入 of negative USD:** no defect. No USD amount is negative in the
  visible input or any hidden case (16,783 honolulu rows, 0 negative), so the rounding direction
  of negatives is never judged.
- **messy-ledger, lb from 2025-01-06 while H1 is lb throughout: defect, fixed.** The truth (ref.py,
  ref_sql.py) reads the export's header (weight_lb for every H1 row, including 2024-12 and
  2025-01-01..05), and no wrong-answer variant targets a per-row switch, so it is not an intended
  trap. Read literally, the note made the Jan 1–5 rows look like kg, which changes q2. NOTES now
  adds that the export writes every row in the header's unit, with records from before the switch
  converted. This is recorded in `ledger/CHANGES.md`, which moves the private-data version.
- **water-ratio, 「給水人口（令和8年3月31日現在）」:** intended, no change. The annual report's table
  is headed 「令和7年度（2025年度）末現在」, which is 2026-03-31. The 2026-04-01 resident count page
  is a listed decoy (the rubric names it as the wrong entity).
- **legacy-billing, BIZ cycle across 2025-04-01:** intended, no change. legacy-codes.md says the
  interval's base fee uses the interval's first day, and intervals are split only by plan_history
  changes (pricing.md). ref_spec.py does the same, and both runs passed 36/36.

## 8. Re-reading older clipped observations

The generic clip hint said 「呼び直すか…」, which is wrong for the budgeted probe: calling again
spends a probe. Two changes:
- `ToolDescriptor.reread` (core): a tool can state how to re-read a clipped result, and the clip
  notice uses it.
- probe (eval): probe appends each call's full results to `scratch/probe_log.jsonl` in work (never
  reverted, not part of any check). Its reread hint points there.

Both conditions get the same change. Other tools keep the generic hint, and re-running a read or
command is the right advice for them.
