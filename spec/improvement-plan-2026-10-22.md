## 3. 個別の改修内容と受入条件

### W01 / N10: コード課題の合否をホスト側で判定する

**現状と原因**

[D群の採点器](../eval/tasks/d/kit.ts) は、提出コードと同じ実行環境が出力した `(pass) [基準ID]` を採点結果として集計する。誤った実装がその文字列を出力して正常終了すると合格することを再現済み。既存のOS隔離はホストへの書込みを防ぐが、子プロセス内での合否の捏造は防げない。

**変更する処理**

1. `CodeTaskSpec` の隠しテストを、ホストが保持する入力ケースと比較処理へ移す。各ケースは `caseId / criterionId / modulePath / exportName / args / expected または比較関数` を持つ。
2. 隔離された子プロセスには、モジュール・関数・引数・ケースIDだけを渡す。期待値、比較関数、隠しテスト本体を子プロセスの読めるファイルや引数に配置しない。
3. 子プロセスは関数の返り値または例外をデータとして返す。ホストが、予定した全ケースについて結果が一度ずつ返ったことと、期待値を満たすことを判定する。子が返す合否フラグやログは判定に使わない。
4. 通信は1回の検証につきケースをまとめて渡す。既存の出力上限・時間制限・隔離を再利用し、ケースごとの大量のプロセス起動を避ける。未知ID、重複ID、欠落、壊れた応答、途中終了は検証不成立とする。
5. 値の形式はJSONで表せる値と、明示的な例外情報に限定する。`undefined`、非有限数、循環参照などを暗黙に`null`へ変換して合格させない。例外ケースは例外名を含む応答をホストで照合する。
6. D群4課題を移行する。`split-bill.ts` の総額0〜59・人数1〜7の全ケース、`RangeError`、税計算維持を含め、既存の隠しテストの検査内容を対応表で照合する。`business-days.ts`、`parse-duration.ts`、`slugify.ts` も同様に移行する。テストファイル未変更の確認は既存のホスト側比較を維持する。

**変更箇所**

[kit.ts](../eval/tasks/d/kit.ts)、[code.ts](../eval/tools/code.ts)、[sandbox.ts](../eval/tools/sandbox.ts)、`eval/tasks/d/` の4課題。ホスト側ケース定義・実行データの形式・回帰試験は同ディレクトリか `eval/tools/test/` に必要最小限で追加する。特定の攻撃文字列を検出する禁止語・正規表現は追加しない。

**受入試験 A01**

- 正常実装は全ケースに合格し、元の誤実装・単に誤った実装・偽の成功ログを出して終了する実装は不合格になる。
- 偽ログの文面や出力順を変えても結果は変わらない。結果の欠落・重複・未知ID・例外・タイムアウトで合格しない。
- 正常な例外仕様と配列の比較が維持される。移行前の全アサーションの検査内容が移行後にも存在する。
- `done` を宣言するシナリオでも、偽装した誤実装は `completed / verified=true` に到達しない。
- macOSとLinuxの隔離試験が成功する。隔離できない環境では従来どおり実行を拒否する。

**完了判定**

実行ログの成功文字列を合否の入力とする経路がなく、A01が成功すること。ケースIDや別の出力チャネルだけを「信頼の証拠」とする変更では完了としない。有限のテストによる仕様適合確認であり、任意プログラムの完全な正しさを保証するものではない。

### W02 / N1: 保存済みの実行結果に対する未完了処理を再開する

**現状と原因**

[engine.ts](../src/domains/loop/engine.ts) は実行結果を `settled` として保存した後に、事後判定・受入確認・ルール評価を行う。この間に中断すると、次の `step` が確認を飛ばして次のツール実行へ進む。保護対象への変更が記録された状態でも再現した。

**変更する処理**

1. 試行ごとの未完了処理を保存する。段階は `need_post_judge → need_acceptance → need_rules → done` とし、設定上不要な段階は明示的に通過させる。
2. ツール結果・特徴量と最初の未完了段階を同一トランザクションで保存する。各段階でも、その段階の結果と次の段階を同一トランザクションで保存する。最後は判断・状態更新と `done` を一緒に確定する。
3. `step` の入口で未完了処理を先に再開する。未完了の確認が解消されるまで、新しい生成要求と副作用のあるツールを開始しない。結果保存済みのツールは再実行しない。
4. 既存の判定失敗時の方針を維持する。判定サービスの失敗は「判定できなかった」と確定・記録し、同じ段階を無制限に再試行しない。中断要求の場合は未完了を残す。
5. 再開時には既存のworkspace digestと照合する。確認対象の状態が変わっていれば、変更前の受入結果を現在の状態の証拠として流用しない。自動的に過去の作業全体を復元しない。
6. 明示的な停止・期限切れでは、終了状態とレポートを先に保存する先行修正を維持する。実行中の未完了処理は終了理由付きで打ち切りを記録し、終端状態から新しい処理を開始しない。

**保存形式と互換性**

[ledger/schema.ts](../src/domains/ledger/schema.ts) 等の公開済みマイグレーションは編集せず、新しいマイグレーションを追加する。試行IDをキーに、段階、対象状態の識別情報、終了理由を保存する小さなテーブルを基本案とする。全体の `PursuitStatus` を増やす必要がなければ増やさない。

旧台帳では、終了済みの履歴は変更しない。実行継続中で最新の `settled` 試行に後処理完了の証拠がない場合は、未完了として復旧対象にする。既存の判定・受入結果を照合し、不足する読取り確認を再実行してからルールを適用する。保護対象変更など既に保存された警告を「旧形式だから」と無視しない。ツール結果そのものが不明な `started` の扱いはW09で扱う。

**変更箇所**

[engine.ts](../src/domains/loop/engine.ts)、[ledger/repository.ts](../src/domains/ledger/repository.ts)、[ledger/types.ts](../src/domains/ledger/types.ts)、台帳の追加マイグレーション、[シナリオ試験](../test/scenario/engine.test.ts)、[SQLite試験](../test/sqlite/ledger.test.ts)。

**受入試験 A02**

- 各保存境界の直前・直後で中断し、同じSQLiteファイルから再開しても、必要な確認が新しいツール実行より先に行われる。
- 保護対象変更を含む試行では、事後判定中に中断しても再開後に介入する。
- 結果保存済みのツール、判断の記録、試行予算が二重に実行・加算されない。
- 判定無効設定、判定失敗、受入確認不要の場合も進行が止まらない。
- 旧形式の継続中台帳を復旧できる。終了済み台帳のレポートと記録は変わらない。

**完了判定**

A02に加え、途中状態の一覧と復旧後の期待状態が対応した状態遷移表を仕様へ残すこと。

### W03 / N6: 採点項目IDの契約を検証する

**現状と原因**

[proof-grader.ts](../eval/tasks/e/proof-grader.ts) は通過IDを集合にするため、同じIDの否定と肯定が混在すると肯定が残る。また、判定されていない低配点項目があっても閾値次第で合格できる。[grader.ts](../eval/tasks/e/grader.ts) も最初に見つかった項目に依存する。

**変更する処理**

1. 期待するチェックポイントと応答について、「全項目が一度ずつ」「未知IDなし」を検証してから採点する共通の小さな検証関数を使う。
2. 重複は内容が同じでも不正とする。順序が違うだけの完全な応答は受け入れる。ルーブリック側のID重複も読込み時に拒否する。
3. `fatal` は発見した致命的誤りの一覧なので、既知IDのみ・重複なしを確認する。全fatal項目の列挙は要求しない。
4. 契約違反は「証明が誤り」ではなく「採点応答が不正」と記録し、合格させない。再要求は既存の呼出し上限・期限内に限定する。正常な応答だけをキャッシュし、ルーブリック内容と採点指示の版もキーに含める。
5. 完全な採点応答に対する重みと閾値の意味は変更しない。低配点項目が明示的に不合格でも、規定の閾値を満たす証明は合格し得る。

**受入試験 A03**

- 肯定・否定の重複を両方の順序で与えても合格しない。欠落、未知ID、同内容の重複も拒否する。
- 全IDを一度ずつ含む応答は、順序に依存せず同じ得点になる。
- 閾値0.8で低配点項目を明示的に不合格とした正規応答は、従来の計算結果を維持する。
- 不正応答はキャッシュされず、異なるルーブリック内容に以前の採点を流用しない。

**完了判定**

両採点器に共通のID整合性検証が入り、A03が成功すること。

### W04 / N7: 数値近似の保証水準を正しく採点者へ渡す

**現状と原因**

[grader.ts](../eval/tasks/e/grader.ts) は `checks` の結果を一律に厳密検証済みと説明する。[mathcheck.py](../eval/tools/mathcheck.py) の数値判定は許容誤差を持つため、非ゼロ値でも近似判定で等しいとされる場合がある。台帳の `numeric` 表示だけでは、既に渡した採点指示を訂正できない。

**変更する処理**

1. [E群kit.ts](../eval/tasks/e/kit.ts) から採点器へ、ホストが実行した検証の式・結果・`assurance` を構造化して渡す。
2. 既存の採点プロンプトを修正し、厳密に確定した結果と数値近似を区別する。数値近似は観測的な根拠として示し、それだけで等式や一般的な証明を保証しない。
3. 提出された `checks` の文面は未信頼の提出データとして扱う。提出者の「厳密に確認済み」という記述をホストの検証結果へ昇格させない。
4. 採点キャッシュのキーに、実際に渡した検証結果と採点指示の版を含める。数値回答を近似で比較する既存の用途は残す。

**受入試験 A04**

- 採点器への要求を捕捉し、`numeric` の結果が厳密保証として説明されないことを確認する。
- 例として `sqrt(2) / 10^60 = 0` の数値判定が通っても、厳密なゼロの根拠として渡らない。別の微小値でも同じ契約が適用される。
- 厳密な有理数計算等は対応する保証水準で渡り、近似回答比較は維持される。
- 同じ証明でも検証結果が異なればキャッシュを共有しない。

**完了判定**

保証水準が検証器から採点要求まで失われず、A04が成功すること。実モデルが常に数学的に正しく採点するという保証は、この機械的な契約試験と分けて評価する。

### W05 / N3: 処理の待機をまたいだ期限を強制する

**現状と原因**

コアは `step` の入口で期限を確認するが、生成や判定を待っている間に期限を超えても、その後のツールを開始できる。ファイル経由LLMの待機上限と、追求の実行期限も別々に存在する。

**変更する処理**

1. 注入済みの `Clock` と相談待ち時間を使い、残りの有効実行時間を共通の純粋な処理で計算する。
2. 生成・事前判定等の待機後と、新しいLLM要求・副作用の開始前に期限と中断要求を再確認する。期限ちょうどを期限切れとする。
3. ホストは残り時間から期限の中断シグナルを作り、利用者の中断と合成して各Portへ渡す。コア内に時刻取得やタイマーを追加しない。
4. 相談待ちは既存契約どおり予算から除外する。相談開始時に実行用タイマーを解除し、回答後に残り時間を再計算する。タイマーとイベント購読は終了時に解放する。
5. 既に生じた副作用の結果が返った場合は、期限切れでも結果保存を飛ばさない。W02の段階記録と終了レポートを整合させ、それ以降の新しい副作用を開始しない。
6. 外部プロセス・APIの中断はホストのPortが担う。中断を無視する任意の外部実装を、コアのシグナルだけで強制停止できるとは扱わない。ファイルLLM待機も追求期限で解除する。

**変更箇所**

[engine.ts](../src/domains/loop/engine.ts)、[rules/checks.ts](../src/domains/rules/checks.ts)、[eval/main.ts](../eval/main.ts)、[file-llm.ts](../standalone/file-llm.ts)、[Port契約](../src/contracts/ports.ts)、[ホスト契約](host-contract-v1.md)。

**受入試験 A05**

- 偽時計で生成中・事前判定中に期限を越えさせ、その後のツール呼出しが0回であることを確認する。
- ホストの期限シグナルで待機が解除される。利用者中断との競合でも終了記録は一つになる。
- 相談待ちを除外し、回答後の残り時間だけ実行できる。古いタイマーで終了しない。
- 副作用後に期限切れになった場合も結果が残る。終了後の遅延応答が終端状態を変更しない。

**完了判定**

コアの境界検査とホストの待機解除の両方があり、A05と先行修正の終了処理試験が成功すること。

### W06 / N5: 同じ知見に異なる根拠を保存する

**現状と原因**

[engine.ts](../src/domains/loop/engine.ts) は種類と本文が一致する知見を既存扱いにする。先に未検証の知見があると、後から採点器が確認した同じ知見が保存されず、検証済みのみを使う設定で見えなくなる。

**変更する処理**

1. 既存のFinding行を再利用し、「主張の同一性」と「根拠の同一性」を分ける。主張は種類・本文の完全一致・適用範囲で識別し、根拠は出典・参照先・保証水準まで含めて識別する。
2. 同じ主張でも新しい検証済み根拠なら別行を追加する。既存の未検証行を消したり、出典を上書きしたりしない。同じ根拠の再受信だけを重複抑止する。
3. 提示時は同じ主張・同じ適用範囲の根拠をまとめ、既存の件数制限を同一主張の重複で埋めない。表示から元のFinding IDと参照先を追えるようにする。
4. ホストが確認した根拠だけに対応する保証水準を付ける。生成側の自己申告で検証済みにしない。異なる前提・戦略範囲の知見を統合せず、数値近似を厳密な証明へ昇格させない。
5. 意味が似ている文章の統合や、反証されたかどうかの判定は本修正でコード化しない。

**変更箇所**

[engine.ts](../src/domains/loop/engine.ts)、[ledger/findings.ts](../src/domains/ledger/findings.ts)、[generation/prompts.ts](../src/domains/generation/prompts.ts)、[知見の仕様](findings-design.md)。

**受入試験 A06**

- 未検証→モデル検証済み、未検証→厳密検証済みの追加で、新しい根拠が保存され `findings=verified` でも提示される。
- 同じ根拠を再保存しても行は増えない。保証水準や出典の異なる根拠は追跡できる。
- 前提・適用範囲の異なる同文の知見は混ざらず、戦略更新後の有効範囲も維持される。
- 数値根拠とモデル評価が併存しても、それだけで厳密保証と表示されない。

**完了判定**

A06が成功し、保存と提示の双方で根拠と適用範囲を確認できること。

### W07 / N9: 有効な設定から実行結果の識別子を作る

**現状と原因**

[eval/main.ts](../eval/main.ts) の再開判定は表示用 `variant` に依存し、言語や一部の判定設定・設定内容を区別しない。日本語で記録した実行が、英語設定では実行済みとして省略されることを再現した。

**変更する処理**

1. ホストで `EffectiveRunConfig` を組み立てる。CLIの指定値だけでなく、既定値・設定ファイルを適用した後の値を使う。
2. 少なくとも、生成・レビュー・採点・批評の要求モデルと推論設定、判定provider・adapter・question set・言語、policy内容、条件フラグ、ツール構成、採点指示・lesson版、課題版、実行コードと依存関係の版を含める。ファイルLLMでは応答方式と申告された応答者情報も記録する。
3. 設定をキー順が安定した形式にしてSHA-256を求め、`configId` とする。ソースは未コミット内容も識別する。生成結果・ログ・一時ファイルはソース識別の対象から除外し、結果が増えるだけでIDが変わらないようにする。
4. `jobKey = taskId + condition + configId + repeat` で再開を判定する。表示名は引き続き人向けのラベルとして使う。
5. APIキー、トークン、認証情報を保存・ハッシュ対象へ含めない。非公開ルーブリック等はホスト内の管理された版IDで識別し、内容や推測可能なハッシュを生成側へ公開しない。
6. 実際に応答したモデルは呼出し後に別項目へ記録する。要求モデルと一致したと推定しない。旧記録は `legacy` として読めるようにするが、新形式の実行を省略する根拠にはしない。
7. [集計処理](../eval/metrics.ts) と [分析処理](../eval/analyze.ts) はconfigIdを保持し、条件が違う結果の混合は明示的に選択した場合だけ行う。

**受入試験 A07**

- 同じ有効設定は再開時に省略し、言語・adapter・policy内容・モデル設定・課題版の変更では新しい実行になる。
- キー順や認証トークンの交換だけではIDが変わらない。結果ファイル追加でも変わらない。
- 旧形式の結果を読み込んでも新形式の実行は省略しない。設定の異なる結果は標準集計で区別される。
- 最大ステップ0等のローカルfixtureで、外部モデルを呼ばずにCLIの実行・再開まで確認する。

**完了判定**

保存形式・再開判定・集計が同じ識別子を使い、A07が成功すること。

### W08 / N8: 全LLM呼出しを実行別に計上する

**現状と原因**

[metrics.ts](../eval/metrics.ts) は主にコア台帳の推論記録から費用を計算する。タスク内部で呼ぶ採点・批評等が実行別の費用から漏れる一方、[settings.ts](../standalone/settings.ts) の共通メーターには記録される。モデル単価が見つからない費用が0相当になる経路もある。

**変更する処理**

1. W07の識別子を使い、`runId / configId / jobId / pursuitId / role / callId` を持つホスト側の利用量記録を作る。roleは生成・レビュー・判定・採点・批評を区別する。
2. `runOne` の開始時にjobの記録範囲を作り、そのjobに結び付いたLLM Portとメーターを生成する。タスク内の採点・批評にも同じjobのPortを渡す。共有メーターの前後差分でjob費用を求めない。
3. 現在共有しているengineはjobごとに生成し、台帳・時計・ID生成器・必要な直列化機構は既存のものを共有する。pursuit作成後にjobとの関連を保存する。同じpursuitの並行stepは許可しない。
4. API応答の利用量は構造化応答の解析より先に保存する。不正なJSONでも発生した利用量は計上する。`callId` の一意性で二重保存を防ぐ。実呼出しのないキャッシュヒットはAPI利用量に加算しない。
5. 要求モデル、応答モデル、入力・出力・キャッシュ読書きトークン、所要時間、成功・失敗、価格表の版を残す。応答が得られず利用量不明の場合は、0ではなく不明と記録する。
6. 費用の正本はホストの利用量台帳に一本化する。コアの推論記録は追跡用に維持するが、二重課金しない。単価不明は `unknown`、保守的推計を表示する場合は `estimated` と明記し、確定額と区別する。
7. RunRecordには内訳、費用の確定・推計・不明の状態を追加する。既存 `usd` の利用箇所を更新し、不明値を0として合算しない。旧形式は帰属不明として残す。ファイルLLMの推定トークンから請求額を捏造しない。

**変更箇所**

[eval/main.ts](../eval/main.ts)、[eval/metrics.ts](../eval/metrics.ts)、[eval/analyze.ts](../eval/analyze.ts)、[standalone/settings.ts](../standalone/settings.ts)、LLMアダプター、評価タスクのPort組立て。ホストの利用量DBは追加テーブルまたは追加列で拡張し、コア台帳とは責任を分ける。現行の全体支出制限は維持し、予約課金方式の全面改修へ広げない。

**受入試験 A08**

- 既知の利用量を返すfixtureで、生成・判定・採点・批評を含む合計が一致する。
- 2jobを並行実行しても費用が混ざらない。job合計と帰属不明分の合計が全体メーターと一致する。
- キャッシュヒット、応答解析失敗、再試行、保存再実行でも二重計上しない。
- 単価不明・利用量不明・旧記録は不明として表示し、0円の実行と区別できる。

**完了判定**

A08と既存の支出制限試験が成功し、全LLM呼出しの保存経路にjobの帰属または帰属不明の理由があること。

### W09 / N2: 中断結果を区別して再試行を制限する

**現状と原因**

[rules/checks.ts](../src/domains/rules/checks.ts) の同条件失敗の検査は主に `settled` を対象とする。中断記録は失敗として残る一方、同じ入力を変更理由なしで再実行できる。全体予算は上限として働くが、個別の再試行ルールを迂回する。

**変更する処理**

1. W10の同一性比較を共通に使い、確定失敗と中断・結果不明を再試行判定の対象へ含める。
2. 中断を「副作用が起きなかった」と解釈しない。結果が分からない試行は、既存のnullable outcome等を使って結果不明として記録する。確定失敗の件数とは分けて提示する。
3. 結果不明の同条件再試行にも、既存の `whatChanged` と回数制限を適用する。変更理由はLLMが説明し、コードは契約上必要な記載と回数を検証する。
4. 再開時は既存の状態・観測と照合する。結果不明のツールを自動で再実行しない。W02で復旧する「結果保存済み・確認未完了」と混同しない。
5. `interrupted` の実行済み予算は引き続き消費したままにする。例外的な自動再試行が必要なら、ホストが宣言する冪等性等の具体的な契約が必要であり、発話やツール名の文字列で決めない。
6. 集計では、確定失敗の繰返しと結果不明の繰返しを区別し、旧記録の集計方法も表示する。

**変更箇所**

[rules/checks.ts](../src/domains/rules/checks.ts)、[ledger/repository.ts](../src/domains/ledger/repository.ts)、[engine.ts](../src/domains/loop/engine.ts)、[eval/metrics.ts](../eval/metrics.ts)、試行の契約とホスト契約。

**受入試験 A09**

- 同じ条件・変更理由なしの再試行は、確定失敗でも中断でも拒否される。
- 副作用直前・直後の中断を別々に再現し、結果不明を成功・副作用なしと誤記録しない。
- workspace状態または意味のある入力が変われば、その条件に対応した判定になる。
- W02の後処理再開ではツールを再実行せず、全体・仮説の予算も重複消費しない。

**完了判定**

W02・W10との結合試験を含めA09が成功し、中断による再試行ルールの抜け道がないこと。

### W10 / N4: 同一性判定で文字列の内容を保持する

**現状と原因**

[fingerprint.ts](../src/domains/rules/fingerprint.ts) は全ての文字列の連続空白をまとめて前後を削る。`A B` と `A  B` のように意味の異なる入力が同じ条件とみなされ、修正した入力が再試行として拒否され得る。開始操作の再送判定 `digestJson` はこの正規化を使わず、本件の対象ではない。

**変更する処理**

1. 新しい指紋は版を明示し、文字列の内容を完全に保持したcanonical JSONから作る。オブジェクトのキー順だけを安定させる。既存の `fingerprintFields` とworkspace digestの役割は維持する。
2. 空白を無視できる外部契約があるツールに限って、ツール側で契約に沿う正規化を行う。入力の種類や個別語句を推測して処理を変えない。
3. 旧版指紋を現在のworkspace digestで一括再計算しない。旧行には当時のdigestが独立して保存されていないため、同じ値を再現できるとは限らない。
4. 旧行との比較は、「現在の候補を旧方式で計算すると旧指紋に一致」かつ「選択された元入力の完全なcanonical JSONが一致」の場合だけ一致とする。旧方式の計算は移行用に隔離する。新規保存は新版だけを使う。
5. 上記はツールの指紋対象フィールド等の契約が同じ場合に限る。旧契約を確認できない場合は履歴照合不能と記録し、再試行を無条件に許可せずレビューへ回す。予算をリセットしない。
6. `digestJson` による開始操作の再送判定は変更しない。旧版・新版の比較制限は集計にも明示する。

**受入試験 A10**

- 連続空白、前後空白、改行、文字列内のコード、Unicodeの違いが保持される。
- 同じ値のオブジェクトはキー順が違っても同じ指紋になる。
- 旧版の同一入力・同一条件は一致し、旧版で潰れていた空白の異なる入力は一致しない。
- workspaceが違う条件は分かれる。旧契約不明の場合は照合不能と分かる。
- 開始操作の再送判定と既存の予算計算に変化がない。

**完了判定**

A10が成功し、文字列の意味をコードが推測する正規化と、移行による履歴の黙示的なリセットがないこと。

### 5.2 結合試験

- **採点の結合**: D群の誤実装を提出→偽ログ→完了宣言まで進めても合格しない。E群では不正IDや数値近似の保証が採点・記録まで一貫する。
- **中断の結合**: 結果保存後に中断→再起動→必要な確認→ルール介入の順序を確認する。期限切れや利用者中断でも終端状態が安定する。
- **履歴の結合**: 旧指紋の失敗・中断履歴を持つ台帳を開き、新版の再試行判定が正しく働く。旧台帳の後処理復旧と組み合わせる。
- **評価記録の結合**: 設定の異なる2jobを並行実行し、実行済み判定・採点・利用量・集計が互いに混ざらない。旧記録を同時に読み込んでも混同しない。

### 5.3 通し検証

結合試験まで成功し、対象の実装を確定してから実行する。

```sh
PURSUIT_LIVE=0 bun run verify
bun run build
git diff --check
```

`verify` に含まれる整形、静的検査、型、コア境界、全自動試験を通す。既存322成功という件数自体を目標にせず、既存試験を削除・弱体化していないこと、新規試験も実行されたことを確認する。

OS隔離に関わるW01は、macOSとLinuxの両方で対象試験を実行する。実行環境が用意できないOSは「未検証」と記録し、そのOSの確認を完了扱いにしない。実モデル用の既存3件は通常のローカル回帰ではスキップ理由を維持する。実モデルでの数学採点精度や長期的な改善率は別の評価結果として記録する。

検証中にコードを編集した場合、その編集に影響される試験結果は無効として取り直す。全通し試験は、未完成の機能による想定内の失敗を追うために繰り返さない。

1. 着手時に作業ツリーと基準試験を記録し、先行5件の修正を含む既存差分を保護する。本書のW単位で対象ファイルと完了条件を確認する。
